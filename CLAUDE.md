# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Max Biocare Raw Materials Procurement** — a Power Apps Canvas App (DesktopOrTablet, 1366×768) that manages the end-to-end procurement request workflow for raw materials. The Power Fx source lives in `.pa.yaml` files.

This folder keeps **only the screen logic + UI** (`Src/`). The generated metadata that the full unpacked `.msapp` would contain (`Controls/`, `References/`, `Resources/`, `Properties.json`, `Header.json`, `AppCheckerResult.sarif`) has been **intentionally removed** — the workflow here is to read/edit Power Fx and paste it into **Power Apps Studio in the browser**, not to repack a `.msapp`. Because of that, this folder can no longer be packed with `pac canvas pack`; re-export from Power Apps if you ever need the full package again.

> Note: the sibling working directory `../ci_cd` is a **separate** Node.js/Docker project, unrelated to this Canvas App. Don't conflate the two.

## Layout

- `Src/*.pa.yaml` — one file per screen (the actual logic + UI). Screen order in `Src/_EditorState.pa.yaml`.
- `Src/App.pa.yaml` — `App.OnStart`: resolves the signed-in user and sets global state.
- `Src/SupplierFollowUpScreen.pa.yaml` — records **one receipt round (round ≥ 2)**, performed by the Requester or the person they assign. Nothing else: the Procurement side of the follow-up moved out to its own screen (below) because the two halves have different actors, and cramming both into one screen made the visibility gating unmanageable once rounds became unbounded.
- `Src/ProcurementFollowUpScreen.pa.yaml` — the **Procurement close-out** (a document step, not a receipt round — see the receiving-loop section). **Procurement/Admin only**; runs **at most once per request** and only on the `Accepted with Adjustment` branch: remarks + Credit Note upload, which also ends the receiving process. Reached from `RequestDetailScreen`'s "Upload Credit Note →" button. Procurement does **not** sit between ordinary receipt rounds — a `Requires Supplier Follow-up` decision opens the next round immediately.
- `Src/DeliveryBatchFormScreen.pa.yaml` — **Procurement/Admin only.** Creates a **Type-2 `Delivery` row** from a parent sitting in `In Delivery`, reached from `RequestDetailScreen`'s "+ Add Delivery" or the parent's row on `HomeScreen`. Procurement enters the quantity arriving in *this* delivery per material (a material left at `0` is simply not in this delivery — the app's existing "quantity > 0 means included" idiom, same as `Filter(colRoundEntry, ReceivedQty > 0)`, so there is no separate include checkbox), plus the delivery's own expected date, its `InvoiceMode`, and notes. It does **not** pick a receiver — see the `GRAssignedToID` note under "Global state" for why that stays `GoodsReceiptScreen`'s job, not Procurement's. On submit it writes the child request row, the child's own `'RM Procurement Line Items'` rows (each with `ParentLineItemID`), bumps the parent's `DeliveryCount`, and writes ExecutionLog **Step 7 on the parent**. Guards: quantity must not exceed what is still outstanding, and it re-reads the parent to abort if the status moved or another delivery took the same number.

  **One button, not two.** When `InvoiceMode = "Direct"`, the same "Create Delivery →" click also attaches the invoice file, extracts it, and files it — all chained inside `formDirectInvoice_DBF.OnSuccess`, with no second button and no pause for manual field review. This was a deliberate simplification over an earlier two-button draft: a delivery is already created by the time the invoice step runs, so leaving that step waiting on a second click would strand a half-invoiced delivery if the user ever navigated away before clicking it. Chaining everything from one click removes that window entirely — the delivery always ends the flow either fully invoiced or cleanly degraded (see below), never half-done.

  **`InvoiceMode` is derived from `ProcurementType` + `InvoiceType`, and only *chosen* when those two guarantee nothing.** `OnVisible` sets

  ```
  gIsViaRequesterBatch =
      ProcurementType = "Invoice Supplied" && InvoiceType = "Official Invoice" && Not(IsBlank(RequesterInvoiceURL))
  ```

  which is the same spine the pre-split `ProcurementExecutionScreen` had (commit `272975a`): its `rowParseInvoice_PE` was visible for `locIsViaRequester || (submit-now && InvoiceType = "Official Invoice")`, and its own official-invoice upload block for `Not(locIsViaRequester) && submit-now && Not(InvoiceType = "Official Invoice")`. **`InvoiceType = "Official Invoice"` is what makes the requester's file *be* the official invoice**; a `Proforma Invoice` is not one, and a `To be sourced by Procurement` request has `InvoiceType` blank.

  | `ProcurementType` | `InvoiceType` | What is guaranteed | UI on the delivery |
  |---|---|---|---|
  | `Invoice Supplied` | `Official Invoice` | one supplier, one invoice, **one delivery** | no picker; `ViaRequester` derived |
  | `Invoice Supplied` | `Proforma Invoice` | nothing | `["Direct", "Deferred"]`, default `Direct` |
  | `To be sourced by Procurement` | *(blank)* | nothing | `["Direct", "Deferred"]`, default `Direct` |

  **The `RequesterInvoiceURL`-only test is not sufficient and was a bug.** `RequestFormScreen`'s `Form1.OnSuccess` writes that column for **every** `Invoice Supplied` request regardless of `InvoiceType`, so deriving the mode from the URL alone made a **Proforma get filed as the official invoice** through `Submit_Invoice`. The `InvoiceType` term is what prevents that — don't drop it.

  **A request-level "single vs multiple invoice" classifier was considered and is deliberately *not* needed.** The tempting design is a column Procurement sets up front (multi-supplier request ⇒ several invoices). It buys nothing: in the `Official Invoice` row the answer is already guaranteed, and in the other two rows `ViaRequester` never applies at all — each delivery simply carries its own `Direct`/`Deferred` invoice, which already works. Note `'Raw Materials'.Supplier` *is* readable (it is the third segment of the `Code · Category · Supplier` subtitle on every line-item table), so distinct-supplier count is derivable if a future rule ever needs it — but no current rule does.

  **One official invoice means exactly one delivery, and that is enforced.** It follows from the round-vs-delivery rule ("a new delivery is a shipment with a new invoice; a further shipment under the same invoice is a round"). `btnAddDelivery` on `HomeScreen` and `btnActionAddDelivery` on `RequestDetailScreen` both hide when `ProcurementType = "Invoice Supplied" && InvoiceType = "Official Invoice" && Coalesce(DeliveryCount, 0) >= 1`, and `btnCreateBatch_DBF` re-checks the same condition on the freshly-read `wLatest` so a second tab can't slip one past. **Keep the three copies in sync.**

  **An earlier draft made `ViaRequester` a third radio option gated on `IsEmpty(Filter(colSiblingBatches, InvoiceMode.Value = "ViaRequester"))` — that was wrong and was reverted.** Its premise was that one requester invoice may cover at most one of several deliveries, so Procurement should pick which. Under the rule above that situation cannot arise: an `Official Invoice` request has exactly one delivery, and in every other case there is no requester invoice to allocate. Don't reintroduce the sibling gate or the third radio option. `colSiblingBatches` is still loaded — it backs the sibling count in the parent-info block — but nothing gates `InvoiceMode` on it.

  **The requester's file is shown even when it is *not* the official invoice, and clearly marked as such.** `rowProformaInvoice_DBF` (beige, sits just above the Direct block so it reads as context for the mode choice) is gated on `Not(gIsViaRequesterBatch) && Not(IsBlank(gSelectedRequest.RequesterInvoiceURL))` — written as "there is a requester file and it is not the official invoice" rather than testing `InvoiceType = "Proforma Invoice"`, so a blank or unexpected `InvoiceType` still surfaces the file instead of silently hiding it. Its title interpolates the real type (`Coalesce(InvoiceType.Value, "Invoice") & " from Requester — reference only"`) and the note says outright that it is not filed. `InvoiceSubmissionScreen`'s `rowRequesterInvoicePreview_ISS` was widened the same way — its gate dropped the `InvoiceMode = "ViaRequester"` term so a Deferred/Direct delivery can still see the proforma when Procurement comes back to file the real invoice, with `lblRequesterInvoiceLabel_ISS` switching between "Invoice submitted by Requester:" and "… — reference only, not filed:".

  **`rowVerifyInvoice_ISS` was deliberately *not* widened.** It carries "Is this invoice correct?" and "Request Re-upload", i.e. the path that files the requester's file as the official invoice — exactly what must never happen to a proforma. It stays `InvoiceMode = "ViaRequester"`-gated, as do the "no requester invoice yet / Remind Requester" block and the two `DisplayMode` gates that pick which URL to parse and submit. Only the read-only preview was opened up.

  **`rowViaRequesterInvoice_DBF`** (`Visible: =gIsViaRequesterBatch`) shows the parent's `RequesterInvoiceURL` as a launchable link plus a required `rdoViaReqInvoiceOK_DBF` (`["Yes", "No"]`) — the port of the old `rdoInvoiceCorrect_PE`. **Yes** files that invoice as this delivery's official invoice through the same extract-and-file chain `Direct` uses. **No** patches the *delivery's* `RequesterInvoiceURL` to `""` and calls `Procurement_Notify_Remind_Invoice.Run(..., gCurrentEmployee.Title)` — same flow and 5-arg shape as `InvoiceSubmissionScreen`'s "Request Re-upload". `Deferred` stays a no-op here: "submit it now" already *is* `Direct`.

  **On the No branch, `InvoiceMode` is deliberately left at `ViaRequester`.** Flipping it to `Deferred` would look tidier but silently reassigns the work: `HomeScreen`'s `btnSubmitInvoice` (the requester's re-upload button) is gated on `InvoiceMode = "ViaRequester"`, so a Deferred delivery would hide it and hand the invoice back to Procurement — the opposite of "ask the requester to re-upload". Leaving the mode alone and clearing only the URL lands the delivery in the exact state the rest of the app already handles: the requester sees "Submit Invoice", Procurement sees "Remind Requester", and `InvoiceSubmissionScreen` shows its no-invoice-yet block. The **parent's** `RequesterInvoiceURL` is left untouched on purpose — it is the requester's original upload record.

  **The extract-and-file chain has exactly one copy, reached through the form in both modes.** `formDirectInvoice_DBF.OnSuccess` no longer composes the invoice URL from `gPendingNewAttName`; it reads the global `gInvoiceFileURL`, which the submit sets per branch — the delivery's own attachment URL for `Direct`, `gSelectedRequest.RequesterInvoiceURL` for `ViaRequester`/Yes. Both branches then do `EditForm` + `SubmitForm` on that same form, so `Parse_Invoice`, the six-field blank check, the filename builder, the `InvoiceSubmitted`/`OfficialInvoiceLink` patch, the Step-6 log row and the 17-arg `Submit_Invoice` all exist once. **`ViaRequester` submits the form with an empty attachment card, inside a container hidden by `Visible: =Not(gIsViaRequesterBatch) && … = "Direct"`, purely to reach `OnSuccess`** — nothing needs uploading, the file is already on the parent's item. That is not a new trick: `RequestFormScreen` already submits `Form1` on its non-invoice path for the same reason. The notify wording was made mode-agnostic ("its invoice could not be filed", not "the invoice file failed to upload") for that reason, and the `Deferred` degradation on failure covers both modes unchanged.

  **`OnVisible` calls `NewForm(formDirectInvoice_DBF)`, never `ResetForm`.** The form's `Item` is `gPendingDeliveryBatch`, which is genuinely `Blank()` until "Create Delivery" runs — the delivery doesn't exist yet while the user is picking the invoice file. `ResetForm` only re-reads the form's *current* `Item`; with a truly blank `Item` that renders nothing to re-read, and in the **published app** (unlike Studio's preview canvas, which is more forgiving) the form gets stuck on a "Getting your data…" placeholder forever. `NewForm` is what `RequestFormScreen.OnVisible` already calls on `Form1` for the exact same reason — its `Item: =gSelectedRequest` binding is likewise resolved *before* the row exists, and `NewForm` is what makes a Form render in create-mode against `Defaults(DataSource)` regardless of what `Item` currently evaluates to. `EditForm(formDirectInvoice_DBF)` right before `SubmitForm` is what switches it back to targeting the real `Item` once `gPendingDeliveryBatch` is set to the just-created row — same two-call handoff `RequestFormScreen` uses for `Form1`/`formRequestFiles`. If a future edit swaps `NewForm` back to `ResetForm` here, the invoice attachment will silently stop rendering in the real app while still looking fine in Studio preview — exactly the bug this note exists to prevent.

  **`Description` is never AI-extracted** — `gInvoiceResult` has no such field (confirmed against `InvoiceSubmissionScreen`'s `txtDescriptionValue_ISS`, which has no `Value:` binding at all and is always typed by hand there). With no human present mid-chain to type one, this screen synthesizes it instead: `"Delivery #" & DeliveryNumber & " of " & <parent Title>`. The six fields that genuinely come from the AI (`invoiceNumber`, `invoiceDate`, `supplierName`, `billedTo`, `totalAmount`, `currency`) are still checked, and a blank among them degrades gracefully: `InvoiceMode` is patched back to `"Deferred"` so the delivery becomes completable later via `InvoiceSubmissionScreen`'s Deferred-mode upload, and the flow ends with a Warning instead of a Success — never blocked, never silently wrong. The same fallback fires if the attachment upload itself fails.
  **Known gap:** if the fallback exhausts (`InvoiceMode` already flipped to `Deferred` once and something fails again — vanishingly rare), the delivery has no further automated recovery path; Procurement would need to intervene directly.
- `Src/ReceiptAmendmentScreen.pa.yaml` — per-request screen (**Procurement/Admin only**, reached via the "Amend Receipt Data" button on that request's row in `HomeScreen`) for correcting what a receiver already recorded: `BatchNumber`, `ExpiryDate`, `QCNumber` and `COALink` on **every** `'RM Procurement Receipt Rounds'` row of that request, any round. **`ReceivedQty` is shown but not editable** — changing a received quantity would silently invalidate `Fulfillment`, the shortfall a Credit Note was already issued against, and the `ReceiptRoundCount`-driven loop state; a wrong quantity is a receiving error to be settled with a further round, not a typo to patch. It **supersedes the old `COACompletionScreen`**, which could only fill a blank `COALink`. See "Receipt data amendment" below — like its predecessor it is intentionally **not** part of the request Status workflow: no execution-log row, no `Status` change.

## Backend & connectors

All data lives in **SharePoint Online** (`maxbiocare.sharepoint.com/sites/Powerapps`). Lists:
- `'RM Procurement Requests'` — the central request record (status, approvers, costs, invoice, goods-receipt, follow-up fields). No longer carries `Category` or `PreferredSupplier` — both moved to the per-material line-item level (see `'Raw Materials'` below).
- `'RM Procurement Line Items'` — one row per raw material on a request (`MaterialID`/`MaterialName`, `Unit`, `Quantity`). Carries **no receipt data at all** — the old `…1`/`…2` received-quantity/batch/expiry/COA columns were deleted when rounds became unbounded.
- `'RM Procurement Receipt Rounds'` — **one row per (line item × receipt round)**, only for materials actually received in that round. This is what makes an unbounded number of receipt rounds possible; the old fixed `…1`/`…2` columns could hold exactly two.
- `'Raw Materials'` — the raw-material catalog. `ID`, `Title` (trade name), `Code`, `Category` and `Supplier` are wired into the app — the last three as the `Code · Category · Supplier` subtitle on the line-item tables that still are tables (`RequestDetailScreen`, `DeliveryBatchFormScreen`), plus a `Category · Supplier` subtitle on the two receipt-entry screens and a Category cell on `RequestFormScreen`. Other catalog columns that may exist on SharePoint are not referenced anywhere in this code.
  - **`Category` (Choice) and `Supplier` (Lookup→`RM Suppliers`) both read through `.Value`.** `Supplier`'s five read sites — `GoodsReceiptScreen` / `SupplierFollowUpScreen` (`Coalesce(LookUp('Raw Materials', ID = ThisItem.MaterialID).Supplier.Value, "")`), `RequestDetailScreen` / `DeliveryBatchFormScreen` (the subtitle), and `RequestFormScreen`'s `lblLineItemSupplier_1` (`Coalesce(ddMaterial_1.Selected.Supplier.Value, "—")`) — mirror `Category`'s exactly, and both were plain text until Aug 2026. A sibling `SupplierID` Lookup (same list, shows `Code`) exists on the list but **nothing in `Src/` reads it**. Don't confuse either with `'RM Procurement Requests'.SupplierSummary` or the log's — that is the SO/PO/INV free-text field and is still Text.
  - **`Category` is a Choice column, so every read is `.Value`.** All five read sites — `RequestDetailScreen`, `DeliveryBatchFormScreen`, `GoodsReceiptScreen`, `SupplierFollowUpScreen` (`wMat.Category.Value`) and `RequestFormScreen`'s `lblLineItemCategory_1` (`Coalesce(ddMaterial_1.Selected.Category.Value, "—")`) — must keep it. `Category` was Text until Aug 2026; a leftover `& wMat.Category` does not degrade gracefully, it errors the entire label, because a Choice record cannot coerce to a string. Nothing filters, sorts or searches on it (`ddMaterial_1`'s `SearchFields`/`DisplayFields` are `["Title","Code"]`), so the change costs no delegation. `ClearCollect(colRawMaterials, 'Raw Materials')` copies the Choice through unchanged, which is why the collection reads identically to the list.
- `'RM User'` — maps an employee to a `Role` (Requester / Manager / Executive / Procurement / Accounting / Admin). **This list is now also the app's membership gate** — an employee must have a row here to use the app at all (see "Global state" and the membership note below). `Requester` must exist as an actual selectable value in this list's `Role` Choice column on SharePoint — that's a SharePoint list-settings change (List settings → `Role` column → edit choices), not something a `.pa.yaml` change can do. Because of this gate, the Goods Receipt / Supplier Follow-up "Assign to someone else" pickers (`ddAssignReceiver_GR`/`ddAssignReceiver_SFU`) are filtered to `Employee List` rows whose `ID` is among active `'RM User'` rows' `EmployeeID.Id` — an employee can only be assigned a receiving task if they can actually log into the app to perform it. Don't widen these pickers back to the full `Employee List` without re-adding some other way for the assignee to gain access.
- `'RM Procurement Approval Log'` — manager/executive decisions (StepNumber 2 = Manager, 3 = Executive).
- `'RM Procurement Execution Log'` — procurement/goods-receipt/follow-up/invoice step records (StepNumber 1 = Procurement Execution, 2 = Accounting Handover, 3 = Goods Receipt **round 1**, 4 = Goods Receipt **round N ≥ 2**, 5 = Supplier Follow-up Procurement **for one round**, 6 = Invoice Submission). Steps 3/4/5 carry `RoundNumber` plus the round's header (`ReceivedBy`, `ReceiptDate`, `ReceiptStatus`, `AcceptanceDecision`, `Notes`, `Attachments`). **There are now multiple step-4 and step-5 rows per request** — never `LookUp` one expecting uniqueness.
- `'Employee List'`, `Project_List` (cross-app list from the sibling `project-list` app).
- `Product_Database_SKU_Master` — external product-SKU catalog. **No longer referenced anywhere in `Src/`** — `RequestFormScreen`'s `cmbSKU` picker (and the `RelatedSKU` write it drove) was removed, and every read-only display of `RelatedSKU` (`RequestDetailScreen`, `ProcurementExecutionScreen`, `InvoiceSubmissionScreen`) was removed along with it. New requests never populate `RelatedSKU`; older requests keep whatever value they already had in SharePoint, just with nothing in the app left to show it. `Product_Database_SKU_Master` can be safely dropped as a connected data source in Studio if nothing else in the app ends up needing it.

- `Procurement_InvoiceData` — cross-app invoice list (owned by the sibling procurement app). **Read-only here**, used solely by the "Project Information" panel on `ManagerReviewScreen` / `ExecutiveApprovalScreen` to compute the related project's Actual Cost: `Filter(Procurement_InvoiceData, ProjectID = gSelectedRequest.ProjectID)` summed by `Currency` over `TotalAmount`. Must be added as a connected data source in Studio. This app never writes to it.

- `'RM Suppliers'` — supplier master, reached **only** through `'Raw Materials'`'s two Lookup columns (`Supplier` → its `Title`, `SupplierID` → its `Code`). It is deliberately **not** a connected data source: a Lookup column already carries `{Id, Value}`, so nothing in `Src/` queries this list directly.

Lists that **no longer exist in the app's code** (removed in a prior refactor — do not reintroduce without checking with the user first): `Suppliers` — the old, unrelated list, not `RM Suppliers`. If it still exists on SharePoint it is currently orphaned/unused by this app.

Full column-level schema (types, choice values, join keys): `docs/sharepoint-schema.md`.

**Power Automate** flows called from Power Fx:

Invoice flows (called from `ProcurementExecutionScreen` and `InvoiceSubmissionScreen`):
- `Parse_Invoice.Run(invoiceUrl, requestId)` — AI invoice extraction.
- `Submit_Invoice.Run(...)` — 17 positional args; writes the official invoice. Param 14 is the invoice **Description** field value and param 17 is the source app name (`"Raw Materials Procurement App"`) — neither is a reserved/empty slot; see `docs/sharepoint-schema.md` for the full param table. The app does **not** pass `ProjectID`: the flow resolves it itself from the request ID (param 2), so don't add an 18th arg back.

General-purpose notification flow — SharePoint flow name **`Procurement Notify`** (renamed from `Procurement_Notify_Receipt_Assignee`), referenced in Power Fx as `ProcurementNotify`:
- `ProcurementNotify.Run(assigneeEmail, assigneeName, requestTitle, requestId, notificationType, deliveryDate, category, sourceApp, displayId)` — **9 args**, identical order at all **8 call sites**. Arg 9 (`displayId`) is `Coalesce(<record>.DisplayID, Text(<record>.ID))` — the human-facing code for the email body; **arg 4 stays the real numeric `ID`** so the flow can still fetch the row. Adding it as a 9th slot rather than retyping arg 4 was deliberate: deleting a Power Automate input and re-adding it as Text moves it to the end anyway, which would have shifted every positional argument. The flow branches on `notificationType`:
  - `"GoodsReceipt"` — new assignee must perform Goods Receipt (round 1). `GoodsReceiptScreen.btnSaveAssignment_GR`.
  - `"SupplierFollowUp"` — new assignee must perform the open receipt round (**round ≥ 2, any round** — the email is deliberately round-agnostic, since the app passes no round number). `SupplierFollowUpScreen.btnSaveAssignment_SFU`.
  - `"Unassigned"` — previous assignee no longer needs to act (email only, no Adaptive Card). Four call sites: `btnSaveAssignment_GR` / `btnSaveAssignment_SFU` (before assigning someone else) and `btnIWillReceive_GR` / `btnIWillReceive_SFU` (requester takes the task back).
  - `"ExecutivePayment"` — `ExecutiveApprovalScreen`, when an approved request is over-threshold: the Executive notifies **themselves** (`gCurrentEmployee.Email`) to go process the payment.
  - `"RMProcurementExecution"` — `ExecutivePaymentScreen`, after the remittance upload, notifies Procurement. **Recipient is hardcoded `"procurement@maxbiocare.com"`**, not resolved from `'RM User'` — verify that address is a real distribution list, or this notification goes nowhere.
  - `category` (arg 7) is **reserved for the request-level Category** and is currently `""` everywhere, because request-level Category no longer exists (it moved per raw-material). Keep it `""` — do **not** repurpose the slot to carry anything else (e.g. a round number). If the email ever needs the round, add a **10th** arg and update all 8 call sites together; Power Fx requires exact arity, so it can't be added incrementally.
  - `sourceApp` (arg 8) is always the literal `"Max Biocare · Raw Materials Procurement"`; the flow prints it in the header and footer.
  - Connection: `app.admin@maxbiocare.com` pinned in "Run only users" — not invoker-provided.

Invoice-reminder flows (called from `RequesterInvoiceScreen` and `InvoiceSubmissionScreen`):
- `Procurement_Notify_Invoice_Provided.Run(requestTitle, requestId, invoiceUrl)` — notifies Procurement after a Requester uploads a corrected invoice.
- `Procurement_Notify_Remind_Invoice.Run(requesterEmail, requesterName, requestTitle, requestIdText, rejectedByOrEmpty)` — "Remind Requester" (last arg `""`) and "Request Re-upload" (last arg = the rejecting employee's name) from `InvoiceSubmissionScreen`.

**Important:** SharePoint system column internal names are English (site locale = en) — use `Title` for the title field and `Attachments` for attachments. Custom columns are also English (`Status`, `EstimatedCost`, `ManagerApproverID`, etc.). `Employee List`'s email column is referenced as both `Email` (in `App.OnStart`'s `LookUp`) and `.email` (everywhere else) — Power Fx matches SharePoint column names case-insensitively, but keep this in mind if a rename ever breaks one usage and not the other.

## Global state (set in App.OnStart)

- `gCurrentEmployee` — row from `Employee List` matched by `User().Email`.
- `gCurrentUser` / `gUserRole` — row from `'RM User'` matched by `EmployeeID.Id = gCurrentEmployee.ID`. **Blank if the employee has no `'RM User'` row** — there is no more synthetic `"Requester"` fallback; a real `'RM User'` row (with `Role = "Requester"`) is required for ordinary requesters too, same as every other role.
- `gIsSpecialRole` — true for Manager/Executive/Procurement/Accounting/Admin (drives toolbar/filter visibility).
- `gSelectedRequest` — the request being viewed/acted on (set before `Navigate`). **May be either a parent or a delivery** — every downstream screen works on whichever it is, because both are rows of the same list.
- `gIsDelivery` / `gRootRequestID` / `gParentRequest` — set in `RequestDetailScreen.OnVisible`. `gIsDelivery` is `RequestType.Value = "Delivery"`; `gRootRequestID` is the parent's ID on a delivery and the row's own ID on a parent; `gParentRequest` is the parent row (blank on a parent). They drive the three reads that must be parent-scoped even when viewing a delivery: `colApprovalLog` (a delivery has no approvals of its own — showing none at all was an audit regression), `colRequirementFiles` (the files are attached to the **parent's** item, so both the name list and the URL's ID come from the parent — this is why `RequirementFiles` is *never* copied onto a delivery, it would 404), and the amber `rowParentLink_RD` banner.
- `gDeliveryNumber` / `colParentLineItems` / `colParentReceived` / `colSiblingBatches` / `colBatchEntry` — `DeliveryBatchFormScreen`'s state. `colBatchEntry` (`{ParentLineItemID, MaterialID, MaterialName, Unit, OrderedQty, DeliveredQty, RemainingQty, BatchQty}`) is the per-material entry buffer, built with `ForAll(colParentLineItems As li, With({wDelivered: Sum(Filter(colParentReceived, ParentLineItemID = li.ID), ReceivedQty)}, …))` — the `As li` alias is **required**, since `ThisRecord` inside the nested `Filter` would otherwise rebind. `ParentLineItemID` is its unique key, so every input writes back with `UpdateIf(colBatchEntry, ParentLineItemID = ThisItem.ParentLineItemID, …)`. `gDeliveryNumber` comes from the parent's `DeliveryCount + 1`, **not** `Max(DeliveryNumber)` over the siblings — the latter still races when two people create a delivery at once.
  **Who receives a delivery is deliberately not decided here.** `DeliveryBatchFormScreen` writes no `GRAssignedToID` at all — the new row is created with it blank, which is exactly what makes `GoodsReceiptScreen.OnVisible` compute `gGRDelegationMode = "I will receive"` (the Requester receives by default) the same way it already does for every other request. Reassigning to someone else is `GoodsReceiptScreen`'s own "Assign to someone else" flow (`ddAssignReceiver_GR`, `btnSaveAssignment_GR`), unchanged. Procurement's screen decides *what* is being delivered and *how the invoice is handled* — not *who* physically receives it; an earlier draft added a receiver picker here and duplicated that mechanism, which was wrong precisely because this is Procurement's screen, not the receiving screen.
- `colDeliveryBatches` — the parent's deliveries, `SortByColumns(Filter('RM Procurement Requests', ParentRequestID = gSelectedRequest.ID), "DeliveryNumber", Ascending)`. Backs `rowBatchSection` on `RequestDetailScreen` (a white **sibling** of `rowInfoBlock`, deliberately *not* a child of it — putting a variable-height gallery inside that no-flexible-child container would mean fighting its `LayoutMinHeight` arithmetic; as a sibling it needs no change to that sum at all).
- `gShowCloseRequest` — the Close Request dialog toggle, reset in `RequestDetailScreen.OnVisible`.
- `gParsingInvoice`, `gHasInvoiceResult`, `gInvoiceResult`, `gShowRejectReason`.
- `gGRDelegationMode` / `gSFU1DelegationMode` — `"I will receive"` vs `"Assign to someone else"` toggle state for Goods Receipt / Supplier Follow-up.

  - **Why the two pickers read collections rather than the lists directly.** The Classic ComboBox's search is not delegable for SharePoint — App Checker flags it on the hidden auto-generated `SearchItems` property (`Search()` is unsupported by this connector). With a data-source `Items` the control pulls the first Data-row-limit rows and searches them **in memory**, so the picker can only ever find within that window, silently. Pointing `Items` at a loaded collection is what removes that; it also turns the search into a *contains* match instead of prefix-only and clears the `SearchItems` warning. Delegated per-use reads (`Filter('Raw Materials', ID = …)`, `LookUp('Raw Materials', Code = …)`) were tried and reverted — they fix `DefaultSelectedItems` and the code paste but leave the picker's search capped, which is the symptom users actually hit.

A plain `ClearCollect` of a whole list emits **no delegation warning at all**, which is exactly how the original 500-row truncation went unnoticed — so each load is followed by an explicit runtime check: `First(Sort(src, ID, SortOrder.Descending)).ID` (`Sort`+`First` *is* delegable, one cheap query) gives the list's true max `ID`, and if the loaded collection's local `Max(col, ID)` comes back lower, the load truncated and a `NotificationType.Error` says so. **Keep those checks** — they are the only thing standing between a growing catalog and materials silently vanishing from the picker.
  - **Do not try to beat the 2000 cap by chunking on `ID`.** `Filter(src, ID > n && ID <= n + 500)` looks delegable but is not: the SharePoint connector delegates only `=` on `ID`, never a range, so every chunk still fetches the first Data-row-limit rows and filters them client-side. The result is identical to a plain load — same ceiling, more queries — and App Checker does flag it (a "Filter" delegation warning on each chunk). This was implemented and reverted; don't reintroduce it. Growing past 2000 needs a genuinely delegable partition key (a plain **Number** column on the list, chunked on that), or a search box driving a delegated `StartsWith` filter as `Items` (unbounded, but prefix-only search and a worse picker), or the catalog moved off SharePoint.

Notes on the parsing:
  - **Line format is `Code Unit Qty`**, e.g. `RM-001 Kg 10`. Only the code is required: the line is split into whitespace-separated tokens and tokens 2/3 are read only when `CountRows(wTokens)` says they exist, so a bare code list still works and falls back to blank unit / quantity 1. Tabs are `Substitute`d to spaces first, so pasting three columns out of Excel behaves the same as typing. **The separator can't be `-`** — the codes themselves contain hyphens (`Code-A`).
  - `Unit` is resolved through `LookUp(["Kg", "g", "L", "ml"] As u, Lower(u.Value) = Lower(wUnitRaw))` rather than taken verbatim: it has to come back in that exact casing or `ddUnit_1.DefaultSelectedItems` (`Table({Value: ThisItem.Unit})`) won't match and the row's unit box renders empty. An unrecognized unit becomes `""` — the row is still added, with a warning saying how many rows need a unit picked. Keep the list in sync with `ddUnit_1.Items`.
  - `Quantity` falls back to `1` unless the token is `IsNumeric` **and** `> 0`, mirroring what `+ Add Material` seeds. A junk quantity never blocks the add; submit validation still rejects the row if it is left invalid.
  - Lines are split on `Char(10)` after `Substitute(…, Char(13), "")` — pasting from Excel/Notepad on Windows yields CRLF, and the stray `Char(13)` would make every code fail to match. Each line is `Trim`ed and blank lines dropped, so a trailing newline is harmless.
  - Matching is `Lower(Code) = Lower(wCode)` against `colRawMaterials`, i.e. case-insensitive, and **per line** — so a repeated code deliberately produces two rows, and input order is preserved. It resolves against the local collection, so it is only as complete as the chunk chain in `OnVisible` — see the `colRawMaterials` note above.
  - Unresolvable codes are skipped rather than added as blank rows (what the feature was asked for), but they are **not** silent: a warning notification lists them. Don't "simplify" that away — a mistyped code that vanishes without a trace is how a material goes missing from a request.
  - The rows are appended in one `Collect(colLineItems, ForAll(Sequence(CountRows(wMatched)) As s, …))` with `RowID: wBase + s.Value`. `Sequence`+`Index` rather than a plain `ForAll(wMatched)` because `ForAll` gives no evaluation-order guarantee, so an inner `Max`/`CountRows` re-read per iteration could hand two rows the same `RowID`; `wBase` is read once and the index supplies the offset.
  - The dialog closes only when **at least one** code resolved. Nothing matching means the user mistyped or pasted the wrong column, and closing would throw the list away — so it stays open with the text intact and an error notification. On success it resets the box before closing, which is also what stops a second `Add` click from duplicating rows.

## Two request types — read this before the workflow

One purchase request's materials arrive from the supplier across **several separate deliveries**, each with its **own supplier invoice** and its own quantities. `'RM Procurement Requests'` therefore holds **two kinds of row**, told apart by `RequestType`:

| | **`Request`** (parent) | **`Delivery`** (child) |
|---|---|---|
| Created by | Requester — `RequestFormScreen` | Procurement — `DeliveryBatchFormScreen` |
| Line items | every material requested | only the materials in *this* delivery, at that delivery's quantity, each carrying `ParentLineItemID` |
| Invoice | **none** — the parent carries no invoice at all any more | its own `InvoiceMode`/`InvoiceSubmitted`/`OfficialInvoiceLink`. **This is what lets one request have many invoices** |
| Receipt rounds | none of its own; rolls its children's up via `ParentRequestID` | its own |
| Title | `ID: <own ID> - <employee> - <dd/mm/yyyy> - <project Title>` | `<parent Title> - #<DeliveryNumber>` |
| Lifecycle | `Pending Manager` → `Pending Executive` → `Pending Procurement` → `In Delivery` → `Delivered` | `Goods Receipt` → `Supplier Follow-up` → `Pending Invoice` → `Pending Accounting` → `Completed` |
| Early exit | `Rejected` (Manager Reject, Executive Reject or Procurement Reject) | `Cancelled` (created in error, only while `ReceiptRoundCount = 0`) |

**The two `Status` sets are disjoint.** That is the load-bearing property of this design: every pre-existing `Status` gate on the downstream screens is already type-safe, so **none of them needed a `RequestType` check added**. `RequestType` is consulted only by `HomeScreen`'s Manager branch and by presentation logic (indent, banner, the Deliveries section, the new buttons).

**Why a child is a row in this same list rather than a separate list.** Three hard constraints all point here, and it's worth not re-litigating: (1) `Submit_Invoice` takes a request ID and **patches `OfficialInvoiceLink` back onto that row itself** — passing the child's ID keeps the flow working untouched *and* gets a per-delivery invoice link, whereas a separate list would force either a flow edit or the parent's link being overwritten once per delivery; (2) a Canvas gallery cannot delegably union two lists, and `HomeScreen` is the app's only worklist; (3) attachment URLs are `gSharePointAttachmentBase & Text(<request ID>) & …`, so a child in the same list needs no URL change anywhere.

What it costs: the child must fill 13 Required ⚠ columns with copies of parent data, and `RequestDetailScreen` still renders some of them (Estimated Cost, Manager Approver, Purchase Accordance, Required Delivery Date). That is a **known, accepted** trade-off, mitigated but not removed by the amber banner on a delivery, `EstimatedCost: 0`, a distinct `ProcurementDescription`, and a SharePoint default view filtered to `RequestType = Request`. If someone does misread a delivery as separately approved, the honest fix is `Visible: =Not(gIsDelivery)` on `rowInfo1`–`rowInfo4` plus a delivery-specific field row — see `docs/sharepoint-schema.md`'s "two request types" table for exactly what a child writes into every column and why.

`DeliveryNumber` is **not** called `BatchNumber` on purpose: `'RM Procurement Receipt Rounds'.BatchNumber` already means the material's *lot* number, and sharing the word made every formula ambiguous.

**Round vs delivery — the rule.** A new **delivery** is a shipment with a **new invoice**. A new **round** inside a delivery is the supplier topping that same shipment up **under the same invoice**. Normally one delivery = one round; the receiving loop below is unchanged and simply scoped inside a delivery now.

**`Completed` now means "this delivery is done", not "the request is done".** One request yields N `Completed` rows and N Step-2 log rows, one per delivery. The parent never reaches `Completed` at all — its terminal state is `Delivered`.

**`In Delivery` breaks an invariant the reminder flows rest on.** For every other status, being in it means work on *that row* is outstanding. An `In Delivery` parent is waiting on its children, not on anyone acting on itself — which is why `Delivered` has to exist to drain it, and why a reminder that nags on `In Delivery` would need to check whether any child is actually open. **Nothing does that today**: no flow notices a parent sitting in `In Delivery` with no delivery ever created. Known gap.

**Executive-payment sub-flow** (`isExecutivePayment` Yes/No field on `'RM Procurement Requests'`): when Executive approves a request that is over-threshold (`Currency <> "AUD" || EstimatedCost > 10000` — `USD` always qualifies since this app only offers `AUD`/`USD`, no FX conversion for the AUD case, just the plain 10,000 cutoff), the request does **not** advance to "Pending Procurement" — it stays `Status = "Pending Executive"` with `isExecutivePayment = true`, and `RequestDetailScreen`/`HomeScreen` display it as **"Pending Payment From Executive"** purely as a computed label (same pattern as the "Supplier Follow-up (Step 1/2)" sub-status — the real `Status` value never changes). The Executive then uses `ExecutivePaymentScreen` (reached via `RequestDetailScreen`'s "Process Payment →" button, shown only when `isExecutivePayment = true`) to upload a remittance advice document; submitting patches `RemittanceURL` and moves `Status` to `"Pending Procurement"` (keeping `isExecutivePayment = true` for history). Unlike the sibling `procurement-procedure` app, there is no Manager fast-track to worry about here — every request that survives Manager review passes through `ExecutiveApprovalScreen`, so the threshold only needs to be checked in one place. `ManagerReviewScreen` no longer *always* routes to `Pending Executive`, though: `Reject` sends it straight to `Rejected`. That doesn't affect the threshold, because a Manager-rejected request never reaches the Executive at all.

`RemittanceURL` now has **one** producer: `ExecutivePaymentScreen`. `ProcurementExecutionScreen`'s own remittance upload was removed together with everything else invoice-related (see below), so `rowFormRemittance_PE` / `rowExecutiveRemittanceInfo_PE` / `formRemittance` no longer exist. `RequestDetailScreen` and the two Procurement work screens still *display* `RemittanceURL` when it is non-blank.

**`ProcurementExecutionScreen` is now parent-only work and carries no invoice handling at all.** It went from ~2790 lines to ~1660. Removed outright: `rdoInvoiceChoice_PE`, `chk5_PE`/`chk6_PE`, the remittance form, `rdoInvoiceCorrect_PE`, the direct official-invoice upload, the whole `rowParseInvoice_PE` block with its 10 parsed fields and `lblSuggestedFilename_PE`, and **both** of its `Submit_Invoice.Run` / `Parse_Invoice.Run` call sites — leaving exactly **one** `Submit_Invoice` call site in the whole app, on `InvoiceSubmissionScreen`. The three-path A/B/C submit collapsed to one Proceed path, and `locIsViaRequester`, `locOfficialInvoiceURL_PE`, `gPendingInvName_PE`, `gPendingPath` are gone. **The Procurement Execution Checklist went too** — `rowChecklistHeader_PE` plus `rowCheck1_PE`–`rowCheck4_PE` (`chk1_PE`–`chk4_PE`), their four `OnVisible` resets, and the `Not(chk1_PE.Checked && … && chk4_PE.Checked)` submit guard. Same reasoning as `ManagerReviewScreen`'s: the tick states were never persisted anywhere, so the boxes gated the submit without recording anything. The Proceed path now validates exactly three things: **SO/PO/INV** (`txtSupplierSummary_PE`) is non-blank, an **Order Confirmation** attachment exists, and **that SO/PO/INV is not already used by another request** — see the uniqueness note below. Removing the rows needed no height arithmetic — they were direct children of `conScrollable_PE`, which scrolls and sums nothing. The `txtSupplierSummary_PE` input (still backed by the `SupplierSummary` column — the column name wasn't renamed, only the label/UX) is a single-line `TextInput` labeled **"SO/PO/INV"**, not the old multiline "Supplier Selection / Negotiation Summary" — it now holds a Sales/Purchase Order or Invoice number rather than a free-text negotiation narrative. The same relabel applies everywhere else this value surfaces: `RequestDetailScreen`'s execution-log detail dialog (`FieldLabel: "SO/PO/INV"`) and `AccountingScreen`'s reference panel (`lblSupplierSummaryRefTitle_AC`). **`InvoiceMode` is now set per delivery** on `DeliveryBatchFormScreen` — *derived* as `ViaRequester` only when `ProcurementType = "Invoice Supplied" && InvoiceType = "Official Invoice"` (which also means that request has exactly one delivery), and *chosen* (`Direct` / `Deferred`, defaulting to `Direct`) in every other case. Same split the old `locIsViaRequester` / `rdoInvoiceChoice_PE` / `InvoiceType` triple enforced here.

**SO/PO/INV is unique across requests, and the check lives in two places on purpose.** The value is stored on the **step-1 execution-log row**, not on the request, so the duplicate test is `LookUp('RM Procurement Execution Log', StepNumber = 1 && SupplierSummary = Trim(txtSupplierSummary_PE.Value) && RequestIDText <> Text(gSelectedRequest.ID))`. `btnSubmit_PE` runs it **before** `SubmitForm(formConfirmation)` so a duplicate is rejected without uploading the attachment first; `formConfirmation.OnSuccess` runs it **again** before its first `Patch`, because the actual write happens after an attachment upload and two people can submit in that window — same re-read-before-write guard `btnSubmitStep1_SFU` / `btnSubmit_PFU` / `btnCreateBatch_DBF` use. The `OnSuccess` copy aborts before the request `Status` is touched, so a losing submit leaves the request in `Pending Procurement` (its attachment does land on the item — harmless, and the alternative is a status change that can't be undone). Both the check and the write use `Trim(…)`, so a trailing space cannot smuggle a duplicate past; `SupplierSummary` is therefore stored trimmed, and the `Title` suffix uses the same trimmed value.
- **The `RequestIDText <> …` term is defensive, not load-bearing** — step 1 runs at most once per request and the screen is only reachable at `Pending Procurement`, so a request never has a step-1 row of its own to collide with. It is written out so that re-entering the screen after a failed write can never flag the request against itself.
- **This requires `SupplierSummary` to be a *single line of text* column on SharePoint.** It is currently multiline, and SharePoint cannot filter a `Note` column at all, so the `LookUp` fails outright until the type is converted — see the ⚠ note in `docs/sharepoint-schema.md`. Index the column while you are there.
- **Nothing enforces this retroactively.** Rows written before the check exists may already share a number; the app only blocks *new* duplicates.

Routing relies on these status strings being exact and consistent across `HomeScreen` (filters + gallery `Items` per-role filter), each action screen, and the `Switch`/`If` color maps. **When changing status names or the flow, update every screen that references the string** — there is no shared constant.

### The receiving loop's state — two fields on the request, not the log

`Status` alone can't say where inside "Supplier Follow-up" a request is, and a per-row `LookUp` into the execution log is non-delegable and too slow for `HomeScreen`'s gallery. The loop's position therefore lives in two plain request columns:

| Field | Meaning |
|---|---|
| `ReceiptRoundCount` | receipt rounds submitted so far — the round being entered next is `+1` |
| `LatestReceiptDecision` | the most recent round's acceptance decision (plain **Text**, so both the round-1 and round-N option sets fit) |

Inside `Status = "Supplier Follow-up"` there are exactly two states:

| `LatestReceiptDecision` | Meaning | Screen |
|---|---|---|
| `Requires Supplier Follow-up` | receipt round `ReceiptRoundCount + 1` is open | `SupplierFollowUpScreen` (Requester / `SFU1AssignedToID`) |
| `Accepted with Adjustment` | Credit Note pending | `ProcurementFollowUpScreen` (Procurement/Admin) |

**Call the Step-5 screen the "Procurement close-out", never a round.** *Round* here means one **goods receipt**: it increments `ReceiptRoundCount` and writes `'RM Procurement Receipt Rounds'` rows (one per line item) with received quantities, batch, expiry, QC, COA. `ProcurementFollowUpScreen` writes none of that — only `CreditNote`, `Fulfillment` and `Status`, plus a Step-5 log row carrying `ExecutedBy`/`ExecutedAt`/`Notes` (and the round number it is closing, which is why `colRoundHistory` hides the attachments button for Step 5: that step has no receipt photos). It is a **document step**: Procurement collects the supplier's Credit Note and ends the receiving process. Two different kinds of work share the single `Supplier Follow-up` status — receiving (the receiver's rounds) and close-out (Procurement's paperwork) — and `LatestReceiptDecision` routes between them. The UI matches: screen title "Procurement Close-out (Round N)", section header "Procurement Close-out — closing Round N", `HomeScreen`'s pill "Procurement Close-out (Credit Note)", `colRoundHistory`'s `StepLabel` "Procurement close-out", and `RequestDetailScreen`'s Step-5 label "Procurement Close-out". The SharePoint choice value `StepName = "Supplier Follow-up — Procurement"` keeps its old text — renaming it means editing the list's choice column.

**Always gate on the pair `(Status, LatestReceiptDecision)`, never on the decision alone** — `gSFURoundOpen` and `gPFUPending` both do. The reason is that `LatestReceiptDecision` is a *historical* field: it records what the latest round decided and is never cleared. After Procurement uploads the Credit Note it still reads `Accepted with Adjustment` forever, so a gate reading only the decision would re-open that screen indefinitely. What actually consumes the pending state is `Status` moving to `Pending Invoice` / `Pending Accounting`; the decision only says *which kind* of work was pending.

The receipt-round side is self-clearing for a different reason — the decision is **overwritten** on every submit, so `Requires Supplier Follow-up` always describes the newest round and therefore means "the next round hasn't been recorded yet". Round N+1's submit replaces it. The `Status` half of that gate is defensive rather than load-bearing, but both gates are written the same way so the invariant is enforced rather than assumed.

`Accepted` never leaves a request in this status at all — whichever screen records it routes straight to Pending Invoice / Pending Accounting. That is also why **no third counter is needed**: an earlier design had Procurement follow up after *every* round and needed a `FollowUpRoundCount` to track whose turn it was. That column was dropped once Procurement was scoped down to the single `Accepted with Adjustment` branch.

`ReceiptRoundCount` is read as `Coalesce(ReceiptRoundCount, 0)` on `HomeScreen`, `RequestDetailScreen`, `SupplierFollowUpScreen` and `ProcurementFollowUpScreen` — purely so a request that hasn't reached Goods Receipt yet reads as `0` rather than blank, **not** as a migration fallback. There is no legacy read path anywhere: the columns those fallbacks used were deleted. Keep the four copies in sync.

Both submit buttons re-read the request and abort if it moved under them — `btnSubmitStep1_SFU` checks `ReceiptRoundCount`, `btnSubmit_PFU` checks that `Status`/`LatestReceiptDecision` still say a Credit Note is owed — so two people acting at once can't create a duplicate round or a duplicate close-out.

**The Credit Note step is gated on the Official Invoice.** A Credit Note is an *adjustment to an invoice*, so the invoice has to exist before one can be recorded against it — that, not screen order, is why Procurement must submit the Official Invoice **before** the Credit Note. Arriving here with no invoice on file is a normal state, not a broken one: goods receipt is what decides whether a follow-up round happens at all, and before this gate existed the close-out simply routed such requests onward to `Pending Invoice`. `ProcurementFollowUpScreen.OnVisible` computes `gPFUInvoiceMissing = gPFUPending && (Not(InvoiceSubmitted) || IsBlank(OfficialInvoiceLink))` — both columns are written together everywhere, but only the link proves the data is there. While it's true the screen swaps the Remarks + Credit Note form and `btnSubmit_PFU` for the amber `rowInvoiceRequired_PFU` block, whose "Submit Invoice →" button does `Set(gInvoiceFromPFU, true); Navigate(InvoiceSubmissionScreen)`; `btnSubmit_PFU` re-checks the same pair on `wLatest`. Because the invoice is guaranteed by then, the close-out patches `Status = "Pending Accounting"` unconditionally.

`gInvoiceFromPFU` is the return ticket for that detour: `InvoiceSubmissionScreen`'s `btnBack_ISS` and all three submit-path navigations do `If(gInvoiceFromPFU, Refresh('RM Procurement Requests'); Navigate(ProcurementFollowUpScreen), Navigate(HomeScreen))` — the `Refresh` is what makes `ProcurementFollowUpScreen.OnVisible`'s `LookUp` see the invoice and unlock the form. Reset to `false` in `App.OnStart`, `HomeScreen.OnVisible` and `ProcurementFollowUpScreen.OnVisible`. Same change exists in the sibling `procurement-procedure` app — keep the two in sync.

**`ExecutiveApprovalScreen` is down to two decisions and ONE always-required text box.** `rdoExecutiveDecision.Items` is `["Approve", "Reject"]` — `Approve with conditions` was removed, so the two approval screens now share one vocabulary. The old two-box arrangement (Approval Conditions on one branch, Rejection Reason on the other) collapsed into a single **Remark**: `rowRejectionReason` / `txtRejectionReason` were deleted outright, and `rowApprovalConditions` lost its `Visible` gate entirely — it is now **always shown and always required**, for both decisions (`Notify("Remark is required")`). The submit's `OnSelect` lost a whole `If` nesting level as a result.

The rule is worth stating because a nested-`If` chain makes the order invisible at a glance: the user only ever sees *one* error at a time, so a chain that starts at the bottom of the form sends them backwards. Apply the same ordering to any new multi-field submit (`ProcurementFollowUpScreen` and the two receipt screens already follow it).

**One remark box means one remark column, and `RejectionReason` is gone from the app entirely.** The string `RejectionReason` no longer appears anywhere in `Src/` — step 2 puts its remark in `ManagerRemarks`, step 3 puts its remark in `ApprovalConditions`, unconditionally in both cases, and nothing reads or writes the old column. (`ProcurementExecutionScreen` still has its *own* "Rejection Reason *" input for a Procurement reject — that one writes to the **Execution** Log and is untouched. Don't confuse the two.) Do **not** re-add a `RejectionReason` write on the Reject branch: `RequestDetailScreen`'s `lblApprovalNoteLine` used to concatenate its non-blank segments, so a row carrying the same text in two columns printed it twice ("Remarks: X · Rejection reason: X"). **No back-compat branches were kept in the approval-history UI** — the user is migrating the old rows by hand in SharePoint, so `RequestDetailScreen` reads the new shape straight:
- `lblDecisionDetail`'s `Color` is `Switch(Decision.Value, "Approve" → green, "Reject" → red, else neutral)`. The `"Approved (within budget)"` and `"Approve with conditions"` arms, and the amber default that covered the two dropped Manager options, are gone.

The separate "Remarks" / "Conditions" / "Rejection Reason" rows are gone — note the old pair differed only by a trailing `s`, which was its own small readability trap.

Two copies of one value is a correctness hazard for no real gain, so the request column was dropped: `ExecutiveApprovalScreen`'s request `Patch` no longer writes it, and both readers now resolve `ApprovalConditions` off the step-3 row — the same thing `ProcurementExecutionScreen` already did.

Only labels moved to "Remark".

**What this change actually shifts is how often that value exists.** It used to be written only on the rare `Approve with conditions` branch, so every read-site treated it as an exception and styled it amber-as-warning per the semantic-colour rule. It is now written on *every* approval, which makes an amber ⚠ on 100% of requests pure noise — so the four read-sites were re-labelled to "Remark" and de-emphasised to neutral grey in the same change: `RequestDetailScreen`'s `rowConditionsText` label and its approval-log note line (whose `Color` collapsed to just red-if-rejection / else grey) and log-detail dialog row, `ProcurementExecutionScreen`'s `rowConditionsBanner_PE` (fill amber → beige `241,239,232`, title "⚠ Executive Approval Conditions" → "Executive Remark"), and `ExecutivePaymentScreen`'s `lblInfoConditionsLabel_EPS`. Note `RequestDetailScreen`'s `rowConditionsText` is gated on `Not(IsBlank(gExecutiveRemark))` and contributes `4 + 80` to `rowInfoBlock.LayoutMinHeight` — that term now fires on essentially every approved request rather than rarely, which is correct but means the block is 84px taller than it used to be in the common case.

`"Approve with conditions"` survives in exactly one place on purpose: the `Decision` colour map in `RequestDetailScreen`'s `lblDecisionDetail`, so historical step-3 rows still render green. Leave the Choice option on the SharePoint column for the same reason.

**`ManagerReviewScreen` has no review checklist, and only two decisions.** The four `chk*` boxes ("Business justification is valid", "Cost is reasonable", "Within approved departmental budget", "Timing and urgency are appropriate") and their `Notify("Please complete all checklist items")` guard were removed outright, together with the four hardcoded `✓` mirror labels (`rowChkReadonly`) that `ExecutiveApprovalScreen` used to show inside `rowManagerChecklist`. Those labels were never data-driven — the checkbox states were **never persisted anywhere**, so the mirror printed four green ticks unconditionally for every request that had passed Manager review; with the checklist gone it would have been asserting something outright false, which is why it went in the same change. `rowManagerChecklist` keeps its name but now holds only Manager Remarks + Manager Decision, and its `Height` dropped `280` → `226`.

`rdoApproved.Items` is `["Approve", "Reject"]`, and **`Reject` is terminal** — `btnSubmitReview` patches `Status = "Rejected"`, so the Manager can now end a request without it reaching the Executive. `Approve` still routes to `Pending Executive`. There is no separate rejection-reason box: `txtManagerRemarks` is required on *every* decision and is the rejection reason when the decision is `Reject`, written to `ManagerRemarks` either way — see the `RejectionReason` note above for why the submit deliberately does *not* also copy it there.

**Both options deliberately reuse the Executive's existing `'RM Procurement Approval Log'.Decision` Choice values, so this change needs no SharePoint list edit at all.** `Approve` rather than `Approved` is the whole point — adding a near-duplicate option to a Choice column buys nothing, and it means `RequestDetailScreen`'s `lblDecisionDetail` colour map already handles the Manager's decision (it has an `"Approve"` → green arm), where an `"Approved"` arm would have had to be added. The trade-off: a step-2 `Approve` and a step-3 `Approve` are now indistinguishable from the `Decision` value alone — **`StepNumber` is what separates them**, which every reader already filters on (`RequestIDText = … && StepNumber = 2`). The three old Manager values (`Approved (within budget)`, `Needs clarification`, `Exceeds budget / unplanned`) are now unwritten; leave them on the column so historical step-2 rows still render.

**`Title` already begins with `ID: <n> - `, so no screen may prepend the ID again.** Ten screens used to render `="ID: " & gSelectedRequest.ID & " - " & gSelectedRequest.Title`; once the ID moved into `Title` itself that produced `ID: 41 - ID: 41 - App Admin - …`. All of them now show the bare `gSelectedRequest.Title`, and the three composite titles dropped their ID segment too (`"Invoice Submission - " & Title`, `"Procurement Execution - " & Title`, `"New Delivery #n - " & Title`). `HomeScreen`'s gallery row shows `ThisItem.Title` on the parent branch; its delivery branch composes its own string and never touched `Title`. If you add a screen, print `Title` alone.

**The escalation concept is gone from the app entirely.** Every request goes through both Manager and Executive approval, so there is no longer such a thing as a request being *escalated* to the Executive — and the leftover UI saying otherwise was removed rather than left to confuse:

Removing a *column* from horizontal `rowInfo4` changes no height.
- The two remaining `SkippedManagerReview: false` writes (`RequestFormScreen`, `DeliveryBatchFormScreen`). The column is not Required ⚠ and nothing reads it any more, so the writes were dead weight. **The column itself is still on SharePoint and still holds `true` on the handful of pre-change requests** — it is simply no longer written or displayed. Don't re-add a reader without deciding what that historical state should mean.

Not to be confused with the **executive-payment** threshold (`isExecutivePayment`), which is alive and unrelated: that is about who pays after approval, not about skipping a level of approval.

### Closing a parent, cancelling a delivery

Both live on `RequestDetailScreen` and are Procurement/Admin only.

**Close Request** (`btnActionCloseRequest` → `rectCloseOverlay_RD`/`conCloseDialog_RD`, the **last two screen-level children**, after the log-detail pair — z-order is child order). Visible only when `Not(gIsDelivery) && Status = "In Delivery"`. The dialog requires `txtCloseRemarks_RD`, shows an advisory line computed from `colLineItemsSummary` saying whether every material was fully received or how many are short, re-reads the request to abort if it moved, then patches `ClosedByID`/`ClosedAt`/`CloseRemarks` and writes ExecutionLog Step 8. **Blocked while a delivery is in any of the receiving/invoicing statuses** (`btnCloseDlgConfirm_RD`'s guard is `Status.Value <> "Completed" && Status.Value <> "Cancelled" && Status.Value <> "Pending Accounting"`) — note `Pending Accounting` is deliberately let through, so **a parent can be closed while a delivery is still sitting in `Pending Accounting`**; see the auto-completion rule below for why that matters. A short delivery is *not* blocked either — the shortfall advisory is advice, never a gate.

`Status` written by this patch is **not unconditionally `"Delivered"`** — `btnCloseDlgConfirm_RD` computes `wHasDeliveries` (at least one delivery exists) and `wAllDelivered` (`wHasDeliveries && IsEmpty(Filter('RM Procurement Requests', ParentRequestID = gSelectedRequest.ID && Status.Value <> "Completed"))`) *before* patching, and writes `Status: {Value: If(wAllDelivered, "Completed", "Delivered")}`. `wHasDeliveries` exists purely to stop the vacuous case — a request can reach this dialog having spawned **zero** deliveries at all (the guard above only blocks on a delivery being *mid-flight*, it never requires one to exist), and an empty `Filter(...)` is `IsEmpty` too, which would otherwise read as "all delivered" for a request nothing was ever delivered against. Step 8 ("Request Closed") is always written regardless of which branch fired, since the user did take the Close action and gave remarks either way; when `wAllDelivered` is true an **additional** ExecutionLog **Step 9** row (`StepName: "Request Completed"`) is written right after it, and the success `Notify` wording branches to say so.

**Cancel** (`btnCancelDelivery_RD`, inside each row of the parent's Deliveries table). Visible only while `ReceiptRoundCount = 0` and the delivery is still at `Goods Receipt`; it re-reads the row and refuses if a round has appeared since render. Patches `Status = "Cancelled"` and reloads `colDeliveryBatches` in place. This exists because a delivery passes no approval screen and round 1 has no `Rejected`, so without it a mistakenly-created delivery would be permanent — and would block the parent from ever being closable.

**A parent can also be promoted from `Delivered` to `Completed` *after* the fact**, for the case the Close-time check above can't catch: a delivery still `Pending Accounting` at the moment of Close (deliberately not blocked, see above) finishing *later*. The check lives in **`AccountingScreen`'s submit** (`btnSubmit_AC`, the only other place a delivery's `Status` is ever patched to `Completed`): right after that delivery's own Patch and its Step-2 log row succeed, it re-reads the delivery's parent (`ParentRequestID`) and, only if the parent is currently `Delivered`, re-queries all siblings (`Filter('RM Procurement Requests', ParentRequestID = wParentID && Status.Value <> "Completed")`) — if that comes back empty (every sibling, including the one just completed, is now `Completed`), it patches the parent to `Status = "Completed"` and writes its own ExecutionLog Step 9 row. Both sites use the identical `Status.Value <> "Completed"` emptiness check; keep them in sync. A parent with even one `Cancelled` delivery never satisfies either check and stays `Delivered` forever — matching that a short/incomplete fulfillment is a deliberate, permanent outcome, not something that should silently read as fully "Completed". **Needs a manual SharePoint change**: add `Request Completed` as a new Choice option on `'RM Procurement Execution Log'.StepName`, same as Steps 7/8 needed when they were introduced.

### Receipt data amendment (decoupled from the Status workflow)

`COALink` on `'RM Procurement Receipt Rounds'` is **required** at submit time on `GoodsReceiptScreen`/`SupplierFollowUpScreen`: both submit handlers reject with *"Please enter Link to COA for all received materials"* when any `colRoundEntry` row with `ReceivedQty > 0` has a blank `COALink` — the same shape as the Batch/Expiry/QC guards that precede it, and it must stay mirrored across the two screens. (There is **no** RM-PK guard: `RMPKCode` is derived, not entered — see the bulk-paste note under Conventions.) Consequently `COAMissing` is written `false` for every new receipt-round row, and the daily reminder flow below only ever surfaces **rows created before that change**.

Fixing anything a receiver got wrong afterwards happens entirely outside the workflow, on **`Src/ReceiptAmendmentScreen.pa.yaml`** — it touches no `Status`, writes no execution-log row, and re-routes nothing.

- **It replaced `COACompletionScreen`, which no longer exists.** That screen listed only rows with `COAMissing = true` and offered only a COA-link input. Once COA became required at submit, its worklist was empty for every new round, while the real need turned out to be broader: a receiver who typed the wrong batch number or quantity had no way to correct it at all. So the screen was generalised rather than kept — same actor, same entry point, same "no Status change" property, but **all five recorded fields are editable on every round**: `ReceivedQty`, `BatchNumber`, `ExpiryDate`, `QCNumber`, `COALink`. `colCOAOutstanding` and `btnCOACompletion_Request` are gone with it; don't reintroduce either name.
- **Entry point:** `btnReceiptAmend_Request` ("Amend Receipt Data") in the row's `rowActions` bar on `HomeScreen`, visible only when the signed-in user is Procurement/Admin, `Status` is neither `Rejected` nor `Cancelled`, and that request already has **at least one receipt round**. `Back()` returns to wherever the user came from.
- **Only changed rows are written.** The save filters `colReceiptAmend` down to rows where any `New…` value differs from its stored twin, aborts with *"No changes to save."* when that set is empty, `Patch`es the rest by `ID`, then reloads the collection so the screen reflects what SharePoint now holds. The screen has **no pinned header**: `rowInfoBlock_RA`, `rowTableHeader_RA` and `galReceiptAmend` are the three children of `conScrollable_RA` (`Y: =60`, `Height: =Parent.Height - 120`), so the whole page scrolls together. It used to position all three absolutely, and the gallery's `Y` drifted onto the column header's `Y` and covered it — an autolayout column cannot make that mistake. `COAMissing` is recomputed on every patched row as `IsBlank(ra.NewCOALink)`, so clearing a link re-raises the flag and the reminder flow picks it up again.
- **The visibility gate uses `Not(IsEmpty(Filter(...)))`, not `CountRows(Filter(...)) > 0`** — `CountRows` over a `Filter` against a SharePoint data source is itself non-delegable (separate from whatever is inside the `Filter`), while `IsEmpty` is. Follow this pattern for any future "does at least one matching row exist" check against a SharePoint list; `CountRows(Filter(...))` is fine only when the source is a local collection (`colReceiptRounds`, `colRoundEntry`, `colReceiptAmend`), never a live data source.

**Why the `COAMissing` flag exists (delegation):** filtering on `IsBlank(COALink)` triggers a Power Apps delegation warning that no formula rewrite can clear — the SharePoint connector never delegates `IsBlank()` on a Text column. `COAMissing` is a Yes/No column computed and written locally (fully delegation-safe to filter on) at the same points the link itself is written: `GoodsReceiptScreen.btnSubmit_GR` and `SupplierFollowUpScreen.btnSubmitStep1_SFU` set it on the rows they create, and `ReceiptAmendmentScreen`'s save recomputes it. **Nothing in the app reads it any more** — its one consumer is the standalone Power Automate flow `RM Procurement - Update COA Reminder for Procurement` (not called from Power Fx; see `docs/daily-coa-completion-reminder-flow.md`), which sends a daily digest to every active `'RM User'` row with `Role = "Procurement"` listing the **requests** that still have at least one row with `COAMissing = Yes`. That flow queries SharePoint directly, so it is unaffected by how any Canvas screen is scoped; it has been repointed at `'RM Procurement Receipt Rounds'` and no longer references the deleted `COA1Missing`/`COA2Missing` columns. It deliberately does **not** exclude Rejected requests — that set is empty in practice, since a request can only be Rejected before any receipt round exists.

### The two Procurement work screens carry the whole requester submission

`InvoiceSubmissionScreen` and `ProcurementExecutionScreen` both open with a beige `rowRequestInfo_*` block listing **every field the Requester filled in on `RequestFormScreen`**, as the first child of their `conScrollable_*`: requester, purchase accordance, procurement type, invoice type, related project (name resolved via `LookUp(Project_List, …)`), estimated cost + currency, budget reference, required delivery date, delivery location, cost center, manager approver, submitted-on, related product SKUs, the full procurement description, **the raw-material line items** (the whole point of a request in this app), and the requirement-file links. `rowReqRemittance_*` adds `RemittanceURL` when it is non-blank — not a requester field, but Procurement needs to know payment already went out. Everything else downstream (`InvoiceMode`, approvals, receipt rounds) is deliberately **not** here — that is what `RequestDetailScreen` is for.

Same shape on both: a 32px header row (bold "Request Details" + status badge), then a `conRequestInfoFields_*` column of 60px four-up field rows, the SKU line, a 96px description, the line-items table, the file links. Both **scroll the block rather than pinning it** — `conScrollable_*` sits at `Y: =60` with `Height: =Parent.Height - 120` (app header 60 + action bar 60), replacing the old `rowInfoBlock_*` pinned at `Y: =60` whose fixed height ate a quarter of the 768px screen before any work was visible. Request identity lives in `lblScreenTitle_*` ("… - ID: n - Title"), which costs no extra height. In both, the block is beige `RGBA(241, 239, 232, 1)` — the "request as it stands" surface `RequestDetailScreen` uses — while the invoice-parsing area (`rowParseInvoice_ISS` / `rowParseInvoice_PE`) is white, so the reference half and the working half read as different surfaces.

**A read-only material list is one 30px row per material — never one crammed line, never a full table.** It went through both extremes first. It started as a trimmed copy of `RequestDetailScreen`'s `rowLineItemsSection` (32px header + 48px-per-row gallery with the `Code · Category · Supplier` subtitle), which cost 92 + 48·n px — over 400px on a typical request — on screens whose actual work sits below it. It was then collapsed to a single `Wrap: =false` line, `Concat(colLineItemsDetail, …, "  ·  ")`, with the full list in `Tooltip`; that fit, but a 5-material request already overflowed at 1366 and the reader had to hover to see what was being bought. The settled form is the middle one: a grey size-9 `"Raw Materials (n)"` caption over a **`TemplateSize: =30` gallery bound straight to `colLineItemsDetail`**, one `RMPKCode — MaterialName (qty unit)` line per row (same string in `Text` and `Tooltip`), plus a sibling `"—"` label gated `Visible: =CountRows(colLineItemsDetail) = 0` for the empty case. No header row, no columns, no subtitle — it costs 20 + 30·n px and needs no hover.
  - **Nine screens carry it, in two naming families that must not be merged.** The `rowInfoMaterials_*` / `galInfoMaterials_*` / `rowInfoMaterialItem_*` / `lblInfoMaterialItemText_*` family on the identity blocks (`AC`, `EPS`, `PFU`, `RA`, `RIS`), and the `rowReqLineItems_*` / `galReqLineItems_*` / `rowReqLineItem_*` / `lblReqLineItemText_*` family on the requester-submission blocks (`PE_1` ManagerReview, `PE_2` ExecutiveApproval, `PE` ProcurementExecution). `InvoiceSubmissionScreen` is the one screen with neither — see `rowReqReceived_ISS` below. **Keep all eight in sync**; the two prefixes exist only because Power Apps rejects a duplicate control name across the app (`PA2110`).
  - **Every copy is a variable-height child, so the container sum above it is variable too.** The row itself is `18 + 2 + Max(1, CountRows(colLineItemsDetail)) * 30` (caption + `LayoutGap` + gallery, `Max(1, …)` so the empty `"—"` still has a line to sit on); the identity block that holds it is `192 + Max(1, CountRows(colLineItemsDetail)) * 30` on `AC`/`PFU`/`RIS`, `300 + …` on `EPS` (a taller block), `162 + …` on `RA`. On `ProcurementExecutionScreen` the row is `44 + Max(1, …) * 30` (its own padding is 8+8 with a 24px caption and a 4px gap) and that same term replaces the old flat `64` in **four** places — `rowRequestInfo_PE` and `conRequestInfoFields_PE`, `Height` + `LayoutMinHeight` each. None of these containers has a flexible child, so a sum that is too small clips the last rows silently.
  - **This is safe only because every one of these blocks now sits inside a scrolling column.** All nine are `FillPortions: =0` children of a `conScrollable_*` with `LayoutOverflowY: =LayoutOverflow.Scroll` and no sibling positioned at an absolute `Y` below them. If a screen ever goes back to a pinned fixed-height header, a material list that grows with the request will push its own work area off screen.
  - **What is genuinely lost is the `Code · Category · Supplier` subtitle** — the row is one line, so `Category`/`Supplier` have nowhere to go. `RMPKCode` is on the line, and `RequestDetailScreen`'s table still shows all three. If an approver ever needs supplier-per-material at decision time, add it to *that* table or to a dialog — don't rebuild a per-screen table.
  - **`InvoiceSubmissionScreen` is the exception: `rowReqLineItems_ISS` was replaced by `rowReqReceived_ISS`, a real table.** It is the screen where an invoice amount is checked against goods, so ordered-vs-received per material is the working data, not reference — the same argument that keeps `ProcurementFollowUpScreen`'s summary a table. It is a control-for-control copy of `AccountingScreen`'s `rowACReceivedHeader` / `galACReceived` (`lblISSRcvCol*` / `galISSReceived` / `lblISSRcv*`, Trade Name · RM Code · Unit · Ordered · Received · Outstanding · Rounds, `TemplateSize: =40`, green "Complete" / red shortfall), reading the same `colPFUSummary` — which `InvoiceSubmissionScreen.OnVisible` now builds itself, along with `colReceiptRounds`, exactly as `AccountingScreen` does. **Keep the two tables in sync.**

### Every work screen must let its actor recognise the request — `rowInfoIdent_*`

`btnDoWork` (and now `btnQVDoWork_HS`) drops the actor straight into a work screen, so that screen's header is the *only* thing telling them which request they are acting on. Seven of them didn't say enough: the pinned `rowInfoBlock_*` carried Title + status badge + one or two step-specific numbers, and `Title` (`ID: n - requester - dd/mm/yyyy - project`) never says **what is being bought**. `AccountingScreen` was the worst case — five checklist ticks and a submit, with nothing on screen naming a single material. Escaping to `RequestDetailScreen` and back was the only recourse, and it costs four navigations.

Each of the seven now ends its `rowInfoBlock_*` with **two** new children:

1. **`rowInfoIdent_*`** — one 44px horizontal row of three columns: `Related Project` (260, resolved via `LookUp(Project_List, ProjectID = …)`), `Required Delivery Date` (170), `Requested by` (200, `Coalesce(RequesterID.Value, RequesterEmail, "—")`).
2. **`rowInfoMaterials_*`** — a **full-width, variable-height** row: an `18px` grey caption carrying the count (`"Raw Materials (" & CountRows(colLineItemsDetail) & ")"`) over a `TemplateSize: =30` gallery on `colLineItemsDetail`, one material per row — see the per-row-gallery rule above for the exact shape and the height arithmetic it forces.

`rowInfoIdent_*` exists on all seven — `GR`, `SFU`, `PFU`, `AC`, `RIS`, `EPS`, `RA` — and is copy-identical apart from the suffix. **`rowInfoMaterials_*` exists on only five of them**: `GoodsReceiptScreen` and `SupplierFollowUpScreen` dropped theirs, because those two screens already put every material on screen in their receipt-entry grid, so the row was a verbatim duplicate sitting above it. **Keep the five in sync.**

- **The materials list gets its own full-width row, not a fourth column in `rowInfoIdent_*`.** It was a column first, and at 1366 that left it ~450px — enough for roughly one and a half material names before the string was cut, on the one field that actually identifies the request.
- **No screen pins this block any more.** Every one of the seven moved `rowInfoBlock_*` inside its scroll container as the first child (`FillPortions: =0` plus a `LayoutMinHeight` equal to its `Height`), and the container went back to `Y: =60` / `Height: =Parent.Height - 120` (`AccountingScreen` is `- 160`, its action bar is 100 tall). The `60 + <block Height> = next control's Y` invariant below is therefore **historical** — keep it only as an explanation of why the numbers used to matter.
- **`ProcurementFollowUpScreen` was the first to be unpinned.** `rowInfoBlock_PFU` was moved *inside* `conScrollable_PFU` as its first child (`FillPortions: =0`, `Height`/`LayoutMinHeight` both `212`), so the whole screen scrolls as one and the container went back to `Y: =60` / `Height: =Parent.Height - 120`. That screen carries two full tables plus the history list, and a 212px pinned header on top of them left almost nothing visible. The `60 + <block Height> = next control's Y` invariant below therefore does **not** apply to it: there is no next control to offset.
- **`rowInfoBlock_*` used to be a pinned, fixed-height container, so the block heights are historical constants worth knowing.** The two rows added `(4 + 44) + (4 + 40) = 92`: `GR`/`SFU`/`PFU`/`AC`/`RIS` went `120 → 212`, `EPS` `228 → 320`, `RA` `90 → 182`, each with a matching `conScrollable_*` `Y`/`Height` shift while the block was still pinned. Those five/320/182 numbers are the base every current formula is derived from — the materials row grew from a flat `40` to `20 + 30·n`, so each block became `<old total − 20> + Max(1, CountRows(colLineItemsDetail)) * 30`: `192 + …` on `AC`/`PFU`/`RIS`, `300 + …` on `EPS`, `162 + …` on `RA`.
- **The cost is real and accepted:** the identity block is now taller than 212 on any request with more than one material, so on the receipt screens the work area starts below the fold. It scrolls, and knowing which request you are receiving was judged worth the scroll — which is also why `GR`/`SFU` dropped the materials row specifically: on those two, the grid below already answers it.
- **`ReceiptAmendmentScreen`, `AccountingScreen`, `RequesterInvoiceScreen` and `ExecutivePaymentScreen` gained a `ClearCollect(colLineItemsDetail, …)` in `OnVisible`** — they never loaded it. Without it the materials line renders **whatever the previously-visited screen left in the global**, i.e. another request's materials, with no error. Any new screen showing this row must load the collection on entry.
- **Do not "solve" this with a `Full Detail →` button on a work screen.** Every work screen's `OnVisible` resets its form (`Reset(rdoDecision_PE)`, `ResetForm(…)`, the `colRoundEntry` rebuild, …), so navigating away and returning silently discards everything typed. That is why the fix is inline information plus a dialog on `HomeScreen`, not a link out.
- `ExecutiveApprovalScreen` displayed no `ProcurementDescription` at all — the Executive approved without the requester's own explanation. `rowDescription_EA` mirrors `ManagerReviewScreen`'s `rowDescription_2` (beige, `LayoutMinHeight: =140`, `Overflow.Scroll` value label) and sits between Purchase Accordance and the Raw Materials table. `containerScroll_2` scrolls and sums nothing, so no height arithmetic was involved.
- The five screens that already carried the full picture — `ProcurementExecutionScreen`, `InvoiceSubmissionScreen`, `DeliveryBatchFormScreen` (`rowRequestInfo_*` / parent-info block) and `ManagerReviewScreen` — were left alone.

### Accounting is a shared queue, not an assignment

There is deliberately **no way to assign a request to a specific Accounting person.** `AccountingHandlerID` is written in exactly one place — `AccountingScreen`'s submit, as `gCurrentEmployee` — so it means *"who completed the accounting step"* and stays blank until the request is `Completed`. `RequestDetailScreen` shows it as "Accounting Completed By".

`ProcurementExecutionScreen` and `InvoiceSubmissionScreen` used to carry an "Assign to Accounting Staff *" picker (`ddAccountingHandler_PE` / `ddAccountingHandler_ISS`, both required to submit) that wrote this field plus the log's `HandoverToID`. All of it was removed, because the assignment was never real:
- It was overwritten twice downstream — by `InvoiceSubmissionScreen`, then unconditionally by `AccountingScreen` with whoever actually clicked submit.
- It gated nothing. `HomeScreen`'s Accounting branch filters on **Status**, not on the assignee, so every Accounting user sees every request in `Pending Accounting` / `Goods Receipt` / `Supplier Follow-up` / `Completed`; `AccountingScreen` has no assignee check either.
- It was picked far too early to be meaningful — at Procurement time the request is only entering Goods Receipt, and with unbounded receipt rounds `Pending Accounting` can be arbitrarily far away.

Don't reintroduce a picker without also making it load-bearing: gate `AccountingScreen`, filter `HomeScreen` by assignee, and stop `AccountingScreen` from overwriting the field. Related gap, currently accepted: **nothing notifies Accounting at any point**, not even when `Status` becomes `Pending Accounting` — they discover work by looking at `HomeScreen`.

## Role-based visibility (HomeScreen)

**One flat list holds both types.** The gallery is sorted `SortByColumns(…, "GroupKey", Descending, "DeliveryNumber", Ascending)`, which puts each parent directly above its own deliveries, newest group first — both columns are Numbers, so it stays delegable. A delivery row is indented (`rowRequestContent.PaddingLeft` 48 vs 16), carries a purple `rectDeliveryAccent` bar, and titles itself `↳ Delivery #n · ID: x · of Request #N`. Known and accepted: if a role's filter matches a delivery but not its parent, the delivery renders "orphaned" with no parent row above it — which is why the row title names its parent.

The gallery `Items` filters `'RM Procurement Requests'` differently per `gUserRole` (always further filtered by `IsBlank(gStatusFilter) || Status.Value = gStatusFilter`):
- **Manager** → `(ManagerApproverID.Id = gCurrentEmployee.ID && RequestType.Value = "Request")`, **or** their own requests (`RequesterEmail = User().Email`). **The `RequestType` term is load-bearing**: `ManagerApproverID` is Required ⚠ so every delivery must copy it, and without the term a manager would see every delivery of every request they ever approved and be able to act on none of them.
- **Procurement** → requests in status `"Pending Procurement"`, **`"In Delivery"`**, **`"Delivered"`**, `"Pending Invoice"`, `"Pending Accounting"`, `"Goods Receipt"`, `"Supplier Follow-up"`, `"Completed"`, **`"Cancelled"`**, `"Rejected"`, or their own requests. Does not include `"Pending Manager"`/`"Pending Executive"`. **`"In Delivery"` is not optional** — without it the parent, the one row Procurement must open to create a delivery, vanishes from their HomeScreen entirely.
- **Accounting** → a narrower version of Procurement's list: `"Pending Accounting"`, `"Goods Receipt"`, `"Supplier Follow-up"`, `"Completed"`, or their own requests. Unchanged by the split — those four statuses now resolve to deliveries only, which is correct: Accounting works per invoice, i.e. per delivery.
- **Executive / Admin** → all requests, unfiltered — so they see both types.
- **Requester (default, and any unrecognized role)** → own requests (`RequesterEmail = User().Email`), plus requests where they're the current Goods Receipt or receipt-round assignee (`GRAssignedToID.Id = gCurrentEmployee.ID || SFU1AssignedToID.Id = gCurrentEmployee.ID`). Unchanged: a delivery copies `RequesterEmail`, so requesters see their own deliveries, and the two assignee columns now only ever exist on a delivery. Note `SFU1AssignedToID` is cleared at the end of every round, so this only matches while a round is actually open and assigned to them.

**`HomeScreen` is the app's work queue, and `btnDoWork` is its primary button.** Each gallery row's `rowActions` leads with `btnDoWork` — one purple button whose `Text`, `OnSelect` and `Visible` are three parallel `Switch(ThisItem.Status.Value, …)` expressions that route straight to the screen where the work happens, skipping `RequestDetailScreen` entirely. It mirrors, gate for gate, the eight action buttons on `RequestDetailScreen`'s action bar (`btnActionReview` / `btnActionExecutivePayment` / `btnActionStart` / `btnActionGoodsReceipt` / `btnActionSupplierFollowUpScreen` / `btnActionProcurementFollowUpScreen` / `btnActionAccounting`), with `ThisItem` substituted for `gSelectedRequest` — **so any change to one set must be made to the other.** There is no shared constant, and a drift means a request is actionable from one screen but not the other.

**There is a third copy of that routing: `btnQVDoWork_HS`, inside the Quick View dialog.** It exists so the actor can confirm *which* request they are about to work on and then start, without the round trip HomeScreen → work screen → Back → Full Detail that reading a gallery row otherwise forces. It reads `gQuickViewRequest`, does `Set(gShowQuickView, false); Set(gSelectedRequest, gQuickViewRequest)` first, and is the **first** child of `rowQuickViewFooter_HS` (which is `LayoutJustifyContent.End`, so first child renders leftmost — work-left, look-right, same as `rowActions`). **Keep all three sets in sync**, with two deliberate divergences from `btnDoWork`:
  - The `Pending Invoice` arm has **no** `Not(InvoiceMode = "ViaRequester" || "Deferred")` negation. That negation exists on the row only because `btnProcessInvoice` sits beside it there; nothing competes inside the dialog, so negating would leave a `ViaRequester` delivery with no route at all.
  - There **is** an `In Delivery` arm → `DeliveryBatchFormScreen`, gated on the same `RequestType = "Request"` + one-official-invoice-one-delivery condition as `btnAddDelivery`. Same reason inverted: the row delegates that status to `btnAddDelivery`, the dialog has no such button. Note this makes a **fourth** copy of the `btnAddDelivery` gate (`HomeScreen` row, `RequestDetailScreen`, `btnCreateBatch_DBF`'s re-check, and now here).

| `Status` | goes to | visible to |
|---|---|---|
| `Pending Manager` | `ManagerReviewScreen` | Admin, or the Manager named in `ManagerApproverID` |
| `Pending Executive` | `ExecutivePaymentScreen` if `isExecutivePayment`, else `ExecutiveApprovalScreen` | Executive / Admin |
| `Pending Procurement` | `ProcurementExecutionScreen` | Procurement / Admin |
| `Pending Invoice` | `InvoiceSubmissionScreen` | Procurement / Admin, **only when `btnProcessInvoice` isn't already showing** |
| `Goods Receipt` | `GoodsReceiptScreen` | the requester, or `GRAssignedToID` |
| `Supplier Follow-up` | `ProcurementFollowUpScreen` if `LatestReceiptDecision = "Accepted with Adjustment"`, else `SupplierFollowUpScreen` | Procurement/Admin for the close-out; the requester or `SFU1AssignedToID` for a round |
| `Pending Accounting` | `AccountingScreen` | Accounting / Executive / Admin |
| anything else | — | nobody (`Switch` default `false`) |

`In Delivery`, `Delivered`, `Completed`, `Rejected` and `Cancelled` deliberately have **no** arm: the first is served by `btnAddDelivery` (Close Request is a dialog and stays on the detail screen), and the rest are terminal. The `Pending Invoice` arm is the one gated negatively — `Not(InvoiceMode = "ViaRequester" || InvoiceMode = "Deferred")` — because `btnProcessInvoice` already covers those two modes with a better label ("Remind Requester" when the requester hasn't uploaded yet). Without that negation the row would show two buttons meaning the same thing; without the arm at all, a `Pending Invoice` row with a blank or `Direct` `InvoiceMode` would have no route to the invoice screen now that the row-click shortcut is gone.

**A `Cancelled` delivery shows only the two look buttons — `btnQuickView` and `btnFullDetail`.** It is terminal and nothing more is ever owed on it, so every action button in `rowActions` must hide. `btnDoWork` and `btnAddDelivery` already do (no `Switch` arm; `RequestType = "Request"`), but the three remaining ones are gated on things a cancelled row can still satisfy — `btnProcessInvoice` and `btnSubmitInvoice` on `InvoiceMode` + `Not(InvoiceSubmitted)` (a delivery cancelled before its invoice was filed matches both), and `btnReceiptAmend_Request` on the existence of receipt rounds. All three therefore carry an explicit `ThisItem.Status.Value <> "Cancelled"` term. The amend button's is defensive rather than load-bearing — cancelling requires `ReceiptRoundCount = 0`, so the row has no rounds to amend — but it is written out so the rule reads the same on all three. `RequestDetailScreen`'s action bar needed no change: all eight of its buttons already gate on a specific `Status`, and `Cancelled` is none of them.

**The row body and `btnFullDetail` both go to `RequestDetailScreen`, unconditionally.** `galRequests.OnSelect` and `rectRowHitArea.OnSelect` used to carry a special case sending Procurement/Admin to `InvoiceSubmissionScreen` when `Status = "Pending Invoice"` — that existed only because there was no work button, and it is gone. A big row-sized hit area should land on a read-only overview, not a mutating form; the explicit buttons are where work starts. `btnViewRequest` ("View", Eye icon) was renamed `btnFullDetail` ("Full Detail") and moved to the end of the bar, next to `btnQuickView`, so the bar reads work-buttons-left, look-buttons-right. Detail is now for the overview and for tracing history when something went wrong — not the way in.

**Every work screen's Back button is `Back()`, not `Navigate(RequestDetailScreen)`.** All ten of them (`ManagerReviewScreen`, `ExecutiveApprovalScreen`, `ProcurementExecutionScreen`, `GoodsReceiptScreen`, `SupplierFollowUpScreen`, `ProcurementFollowUpScreen`, `AccountingScreen`, `ExecutivePaymentScreen`, `DeliveryBatchFormScreen`, `ReceiptAmendmentScreen`) hard-coded the detail screen, which was already wrong for `ReceiptAmendmentScreen` (only ever reached from `HomeScreen`) and became wrong for the rest the moment `btnDoWork` existed — Back would dump the user on a screen they never visited. `Back()` returns to whichever screen they actually came from. Submit-success navigations were **not** changed: `ProcurementExecutionScreen` and `DeliveryBatchFormScreen` still `Navigate(RequestDetailScreen)` on success, deliberately, because after submitting you want to see the result.

`btnAddDelivery` sits in each row's `rowActions` bar, visible only when `RequestType = "Request" && Status = "In Delivery"` and the user is Procurement/Admin. `btnSubmitInvoice` and `btnProcessInvoice` gate on `InvoiceMode`, and `btnReceiptAmend_Request` filters receipt rounds by `RequestIDText = Text(ThisItem.ID)` — all three therefore **self-hide on a parent** with no `RequestType` term needed, since a parent has no `InvoiceMode` and no receipt rounds of its own.

The filter bar gained `In Delivery`, `Delivered` and `Cancelled` pills. It did not need shortening to fit: `rowFilterBar` sets `LayoutOverflowX: =LayoutOverflow.Scroll`, so pills just append and the bar scrolls.

The status pill for `"Supplier Follow-up"` is a **computed sub-status**, same pattern as "Pending Payment From Executive" — the real `Status` string never changes inside the loop. It renders `"Procurement Close-out (Credit Note)"` when `LatestReceiptDecision = "Accepted with Adjustment"`, otherwise `"Goods Receipt (Round <n+1>)"`. It reads only `ThisItem.*` fields — no `LookUp` — which is both delegable and faster than the old Step-4 log probe it replaced.

Filter buttons and "+ New Request" are **not** role-gated — every user who passes the membership gate (`Not(IsBlank(gCurrentEmployee.ID)) && Not(IsBlank(gCurrentUser.ID))`) sees the same filter bar and "+ New Request" button; only the underlying gallery `Items` differ per role. Keep the per-role `Items` filter in sync when adding new statuses, but don't assume the buttons themselves need per-role `Visible` logic — they currently don't have any.

## Display ID vs record ID

`'RM Procurement Requests'` holds both parents and deliveries, so SharePoint's auto-`ID` skips numbers from a requester's point of view (request 1, then deliveries 2 and 3, then request 4). Three columns give humans a dense, typed code without touching any logic:

| Column | Meaning |
|---|---|
| `RequestYear` (Number) | two-digit year the **parent** was created, e.g. `26`; a delivery copies its parent's |
| `RequestSeq` (Number) | sequence **within that year**, allocated to parents only; a delivery copies its parent's |
| `DisplayID` (Text) | `RMRQ-26-0001` on a parent, `RMRQ-26-0001-D1` on a delivery |

- **`DisplayID` is never a key.** Every `LookUp`, `Filter`, `RequestIDText`, attachment URL and flow parameter still uses the real `ID`. If you catch yourself matching on `DisplayID`, you have introduced a bug: it is not unique across years if the counter is ever reset by hand, and it is editable in SharePoint.
- **Allocation lives in `RequestFormScreen`'s second `Patch`** — the one that already ran after the row exists to write `GroupKey`. Next number comes from `First(SortByColumns(Filter(…), "RequestSeq", Descending)).RequestSeq + 1`; `Max()` is deliberately avoided because the SharePoint connector does not delegate it, while `Sort`+`First` does (the same trick the `colRawMaterials` truncation check uses).
- **A collision re-check follows immediately**, mirroring how `btnCreateBatch_DBF` guards `DeliveryNumber`: read back the rows sharing this year+seq, and if the lowest `ID` among them is not ours, take `seq + 1` and re-patch. Two simultaneous submits therefore cannot end up with the same code.
- **The code is embedded at the *front* of `Title`**, which is why ~15 screens that print `Title` needed no change. That position matters: `ProcurementExecutionScreen` appends the SO/PO/INV summary to `Title` later, so anything at the end would be pushed around.
- **A delivery's `Title` is `Substitute(parent.Title, parent.DisplayID, <own DisplayID>)`** — it swaps the parent's code for its own and keeps requester/date/whatever else was appended, instead of the old `<parent Title> - #n` which duplicated nothing but also carried the parent's code unchanged.
- **`DisplayID` is not a sort key.** `HomeScreen` still sorts `GroupKey` desc + `DeliveryNumber` asc — both Numbers, both delegable. Sorting on the text code would break grouping and delegation at once.
- Every read site uses `Coalesce(DisplayID, <old ID expression>)` so rows created before this change still render something rather than a blank.

## Conventions

- All UI text, field names, comments, and code are **English** (per global instruction). Vietnamese appears only as SharePoint system-column internal names and the `vi-VN` UserLocale.
- Patches use the `With({wPatched: Patch(...)}, If(IsBlank(wPatched.ID), Notify(error), ...success...))` pattern to guard against write failures — follow it for new writes.
- **A double quote inside a Power Fx string is escaped by doubling it (`""`), never with a backslash.** `\"` is not an escape — Studio rejects it with *"Unexpected characters"* / *"Expected operator"*, because `\` ends the literal and the rest of the line becomes garbage. This bites when writing English prose into a `Notify` or label that quotes a UI element by name. The existing `Substitute(…, """", "")` calls in `DeliveryBatchFormScreen`/`InvoiceSubmissionScreen` (stripping `"` out of a filename) are the correct form; the neighbouring `"\\"` in those same chains is a *backslash literal*, not an escape, and is unrelated. Easiest fix is usually to reword so the quotes aren't needed at all.
- **Attachment cards bound to `'RM Procurement Requests'.{Attachments}` always set `Default: =Blank()`.** That column belongs to the request, not to a step, and six screens append to it (request form, `RequesterInvoiceScreen`, `ProcurementExecutionScreen` ×3, `InvoiceSubmissionScreen`, `ProcurementFollowUpScreen`). A blank Default means the control starts empty and only reports the file just added — which is what makes the standard `If(CountRows(attX.Attachments) = 0, Notify("… is required", …), Set(gPending…Name, Last(attX.Attachments).Name); SubmitForm(…))` guard correct, and what lets `OnSuccess` build the file URL from `Last(...).Name`. Existing attachments are untouched by the submit. Do **not** point Default at the record's attachments (`gSelectedRequest.Attachments` / `ThisItem.Attachments`) on these cards: the control then edits that same collection in place, so any "did the count grow?" check compares a value against itself and rejects every submit — this is exactly how `btnSubmit_PFU` came to reject Credit Notes that had in fact been attached. (The Goods Receipt / Supplier Follow-up photo cards are a different case — they bind to the *log row's* attachments via a gallery `ThisItem`, and use `gGRPendingAttachments`/`gSFU1PendingAttachments` to survive a re-render.)
- `RequestIDText` (text copy of the request ID) is used to look up log rows. **Steps 1/2/6 are unique per request and can still be `LookUp`ed; steps 3/4/5 are not** — there is one row per receipt round, so filter and sort them instead.
- Colors are inline `RGBA(...)`; brand purple is `RGBA(83, 74, 183, 1)`.
- **A link is never rendered as its own URL.** Every clickable link label reads `If(IsBlank(<col>), <blank text>, "Open <thing> ↗")` with `Tooltip: =<col>` carrying the real URL, plus the existing `OnSelect: =If(Not(IsBlank(<col>)), Launch(<col>, {}, LaunchTarget.New))` and `Underline: =Not(IsBlank(<col>))`. SharePoint attachment URLs are long, opaque and `EncodeUrl`-escaped, so printing one filled a fixed-height `Wrap: =false` label with a truncated string that told the reader nothing; the tooltip is what keeps the URL recoverable for anyone who needs to copy it. Applies to all 20 link labels across nine screens — `RequesterInvoiceURL`, `RemittanceURL`, `OfficialInvoiceLink`, `PurchaseOrderLink`, `CreditNote`, `COALink`. The blank branch keeps whatever the screen already said (`"—"`, `"Not linked"`, `"Missing"`, `"Not submitted"`, `"Not uploaded"`, `"Not provided"`) — those differ by context and are deliberately not unified. The `↗` is part of the string on **all** of them; the four labels that predated this rule without it (`"Open invoice"`, three copies of `"Open COA"`) were normalized in the same change, which matters for the COA one because it lives in the copy-identical round-details dialog on three screens.
  - **One exception, deliberately.** Galleries over `colRequirementFiles` / `colReceiptPhotos` show `FileName` / `DisplayName` and launch `FileURL` / `AbsoluteUri` — a real file name is more informative than "Open file", so they stay. `RequestDetailScreen`'s generic step-details dialog used to be a second exception — it printed raw URLs because its `{FieldLabel, FieldValue}` gallery had no `OnSelect`. It now follows the rule instead: a third column `FieldURL` drives `OnSelect`/`Underline`/`Tooltip` per row, so `Purchase Order Link` and `Order Confirmation` read "Open … ↗" and launch like everywhere else.
- **Surfaces and table style (`RequestDetailScreen`).** The screen had drifted into three near-identical light beiges (`241,239,232` for `rowInfoBlock`, `225,223,214` for the Raw Materials header, `248,247,243` for every gallery's zebra) — too close together to create hierarchy, and the history galleries striped in *exactly* the info block's beige so they read as a continuation of it. The rule now is:
  - **Beige `RGBA(241, 239, 232, 1)` = the request as it stands.** Only `rowInfoBlock`. That is why `rowCreditNote` moved up into it, next to the other document links.
  - **White `RGBA(255, 255, 255, 1)` = history.** The three sibling sections `rowGRSection` / `rowApprovalSection` / `rowExecutionSection`, each `PaddingTop 20` / `PaddingBottom 16` / `PaddingLeft`+`Right 20`, `LayoutGap 6`, one 28px Bold size-11 title, an optional grey size-9 summary line, then header + gallery.
  - **One table style everywhere:** header row 32px filled `RGBA(232, 230, 221, 1)` with size-9 Semibold `RGBA(107, 105, 98, 1)` labels; rows plain white with a 1px `RGBA(232, 230, 221, 1)` hairline as the **last child of the row template** (so the template is vertical: `…Body` at `TemplateSize − 1`, then the rule). **No zebra striping** — one separation mechanism per table, not three.
  - **History row geometry is shared by all three tables:** `TemplateSize: =52`, `TemplatePadding: =0`, body 51px with `PaddingTop`/`Bottom 4` and `LayoutGap 10`, a fixed **96px two-line timestamp column** (`dd/mm/yyyy` size-10 Semibold over `hh:mm` size-9 grey) then a `FillPortions: =1` column holding a 24px cells row and a 15px notes line. Section height is `108 + CountRows(...) * 52` (`134 + …` for `rowGRSection`, which has the extra summary line) — change the row height and all four numbers move together.
  - **Status badges use the 12-hue per-status palette**, not the old grouped one — and **every status badge in the app now carries it**, not just the two overview screens. One distinct hue per `Status` value (amber Pending Manager · orange Pending Executive · olive Pending Procurement · purple In Delivery · teal Delivered · red Rejected · blue Goods Receipt · cyan Supplier Follow-up · violet Pending Invoice · magenta Pending Accounting · green Completed · muted-rose Cancelled), as a `Color`/`Fill` `Switch` pair with a neutral `RGBA(68, 68, 65, 1)` / `RGBA(241, 239, 232, 1)` default arm. This deliberately spends blue and violet on badges, which the link/chrome reservations below otherwise forbid; a badge is an outcome, not chrome. The computed sub-status labels ("Pending Payment From Executive", "Procurement Close-out (Credit Note)", "Goods Receipt (Round N)") intentionally share their parent status's hue.
    - **Eleven copies, no shared constant — keep them in sync.** `HomeScreen`'s `lblRequestStatus`, `RequestDetailScreen`'s `lblStatusBadge`, and the nine work screens' `lblStatusBadge_{GR,SFU,PFU,AC,RIS,RA,EPS,PE,ISS}`. The two overview copies key off `ThisItem`/`gSelectedRequest`; the nine work-screen copies all key off `gSelectedRequest`. A twelfth, `lblBatchStatus_RD` (the Deliveries table), lists **only the six delivery statuses** since a delivery can hold no other — don't paste the 12-arm version over it.
    - **Badges carry no border.** `BorderColor`/`BorderThickness` were removed from all nine work-screen badges: the palette's paired fill+text hue is the whole signal, and a border in the same hue just muddied it at `Size: =10`. Don't add one back to a single screen.
    - The nine work-screen badges previously hardcoded one colour each — five amber `133,79,11`, two orange `246,88,16` (`SupplierFollowUpScreen`/`ProcurementFollowUpScreen`), and `InvoiceSubmissionScreen` had its own partial 4-arm map. They therefore lied whenever the row's real status wasn't the hardcoded one, most visibly on a `Cancelled` delivery rendering amber-as-pending. That is what this change fixed; a fresh hardcoded badge would reintroduce it.
    - **`Text` was deliberately left alone.** Only `Color`/`Fill` were unified. `HomeScreen` computes the sub-status in its badge text (Round N, Close-out, Payment-From-Executive) because a gallery row has no other place to say it; the work screens print the bare `Status.Value` and carry the same information in their own fields right below (`Closing receipt round`, `Receipt Rounds Completed`, `Receiver's Acceptance Decision`), and `ExecutivePaymentScreen` hardcodes `"Pending Payment From Executive"` since it is only ever reached in that state. Unifying the text would duplicate those fields, not clarify them.
  - **Semantic colors are reserved for outcomes**, never chrome: green `15,110,86` accepted/approved, red `163,45,45` rejected, amber `133,79,11` needs attention. Blue `56,96,178` is links only. Purple `83,74,183` is the app header, dialog titles and primary buttons only — it is deliberately *not* used for the "Round N" cell any more, so it stops competing with the buttons in the same row.
  - The two pre-existing receipt dialogs (`conPhotoDialog_RD`, `conRoundDetailDialog_RD`) still use the old header beige `241,239,232`. They were left alone on purpose: those blocks are copy-identical across three screens (see `colRoundDetails` above), so restyling them means editing `SupplierFollowUpScreen` and `ProcurementFollowUpScreen` in the same change.
- The four receipt dropdowns hold their options as **inline literal tables**, not `Choices()` — the backing SharePoint columns are gone. A literal `["a", "b"]` is a one-column table whose column is named `Value`, so `.Selected.Value` reads the same as it did with `Choices()`. Changing an option is now a code edit pasted into Studio; and since `LatestReceiptDecision` / the log's `AcceptanceDecision`/`ReceiptStatus` store these as plain text, renaming an option also means updating every `= "..."` comparison in the receiving loop.
  - `ddReceiptStatus_GR`, `ddReceiptStatus2_SFU` → `Fully Received` · `Partially Received` · `Incorrect Items` · `Damaged Items`
  - `ddAcceptanceDecision_GR` (round 1) → `Accepted` · `Requires Supplier Follow-up`
  - `ddAcceptanceDecision2_SFU` (round ≥ 2) → `Requires Supplier Follow-up` · `Accepted` · `Accepted with Adjustment`
  - Round 1 deliberately has **no `Rejected`** — a bad delivery goes into the receiving loop instead of terminating the request. The `Rejected` *Status* value is untouched; Manager/Executive/Procurement still set it.
- **The bulk receipt paste (`txtBulkReceiptGR` / `txtBulkReceipt_SFU`) is positional — one line per material, in table order, no key column.** Each line is `QC Number · Batch No · Expiry Date (dd/mm/yyyy) · Received Qty · Link to COA`, space- or tab-separated, matching the on-screen column order so a user reading a row left-to-right types the fields in the same sequence. Line *n* fills row *n* of `colRoundEntry`, resolved with `Index(colRoundEntry, s.Value)` over `Sequence(CountRows(wLines))`.
  - **Positional is safe here only because nothing sorts the gallery.** `galLineItemsGR.Items` / `galLineItems_SFU.Items` are plain `colRoundEntry` with no `Sort`/`SortByColumns`, and that collection is built once in `OnVisible` from `colLineItemsDetail` — so screen order *is* collection order for the life of the screen. **If a sort is ever added to either gallery this paste silently writes to the wrong materials**; it would have to sort identically, or go back to a key.
  - **The count guard is what makes a bad paste loud instead of silent.** `CountRows(wLines) <> CountRows(colRoundEntry)` aborts with a message naming both numbers and applies *nothing*. Without it one missing line shifts every row after it, writing B's batch number onto A with no error — the single failure mode positional matching has. Don't relax it into "apply what lines up".
  - **`-` is the skip marker**, needed because positional tokens can't omit a field in the middle: `-` in a field leaves that field unchanged, and a line containing only `-` leaves the whole material untouched. Blank/missing trailing fields behave the same. `Received Qty` and `Expiry Date` need no explicit `-` case — a non-numeric token fails `IsNumeric`, and `-` doesn't split into three date parts, so both already fall through to the existing value; `QC Number`, `Batch No` and `Link to COA` are free text and do test for it.
  - **`lblBulkReceiptOrder_*` exists because the dialog covers the table it refers to.** It lists `1. <material>` per row off the same `colRoundEntry`, so the ordering the format depends on is readable while pasting. That is why the dialog grew `440 → 560` — `Height`, `X` and `Y` all reference that number.
  - **This replaced an `RM Code`-keyed format** (`Code · Qty · Batch · Expiry · QC`). The key was dropped because `RMPKCode` is not the receiver's to supply: it is seeded in `OnVisible` from `LookUp('Raw Materials', ID = wMatID).Code` and rendered by a **Label** (`lblGRItemRMCode`), never an input, so requiring it made them transcribe a value the app already had. That format had its own quiet failure too — a mistyped code was merely "skipped".
  - Three places encode the field order and must change together on **both** screens: the `wQCRaw`/`wBatchRaw`/`wExpiryRaw`/`wQtyRaw`/`wCOARaw` token indexes in the Apply button, the hint label, and the `Placeholder`.
  - **`Link to COA` is last, and that placement is what makes it safe to include.** It was left out at first on the theory that a URL breaks a space-separated format; only the space would, since `/` is split on nowhere but the expiry token — and a real URL encodes spaces as `%20`. Being the final field also means a future change could take "everything after token 4" instead of token 5 if a space-bearing link ever turns up. Filling COA here is what keeps `COAMissing` false without a second pass through `ReceiptAmendmentScreen`.
